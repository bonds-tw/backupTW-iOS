# A. TWDIW

## A1. 選擇性揭露會送出使用者沒有勾選的欄位

**狀態：可以送。** 證據充足、可重現、後果直接落在使用者身上。

皮夾 SDK 決定保留哪些 disclosure 的方式，是**把要求的欄位名拿去跟整個解碼後的
JSON 陣列做子字串比對**——而那個陣列裡包含 salt 與值：

```
String decoded = utf8.decode(base64.decode(base64Url));
if (decoded.contains(field)) { … }
```

所以一個要求 `name` 的查驗方，會拿到任何 salt 或值裡剛好出現 `name` 這四個字元的
欄位。**使用者以為自己揭露了一個欄位，實際上揭露了兩個**，而畫面上不會顯示這件事。

建議：比對 disclosure 解碼後陣列的**第二個元素**（claim name），而不是整串。

## A2. 四個對外請求關掉了 TLS 主機名驗證

**狀態：可以送，但要先確認是否已修。** 這是最像「開發時期留下來忘了拿掉」的一條。

關掉主機名驗證，等於任何持有一張有效憑證的人都可以冒充發行端。它出現在四個 fetch
上，其中包含取 JWKS 的那一個——也就是決定「這份憑證的簽章要用哪把公鑰驗」的那一個。

## A3. 狀態清單與 schema 在驗證發行者簽章之前就被抓取

**狀態：可以送。**

`credentialStatus.statusListCredential` 與 `credentialSchema.id` 都是憑證裡的
URL，而它們在簽章驗證之前就被 fetch。一張未經驗證的憑證因此可以指使皮夾去連任何
位址——是一個由憑證內容決定的對外連線，在憑證本身還沒被信任的時候。

## A4. `client_id` 不具鑑別力，而兩個檢查是關掉的

**狀態：可以送，但措辭要小心。**

`client_id` 是一個 echo，不是註冊表；ID Token 的簽章沒有被驗證；
`AccessTokenFilter` 被註解掉。合起來的意思是**第三方皮夾這個角色目前不存在**——
不是被拒絕，是沒有機制分辨。

⚠️ 措辭上不要寫成「任何人都能假冒官方皮夾」，因為那需要另外的前提。準確的說法是
「皮夾的身分在這個流程裡沒有被鑑別」。

## A5. `format` 與實際回傳的東西不符

**狀態：可以送。**

issuer metadata 對 **882 組憑證設定全部**寫 `"format": "jwt_vc_json"`，而實際回傳
的是 `vc+sd-jwt` 加 `~` 分隔的 disclosure 串。整份 701 KB 的文件裡 `sd-jwt` 這個
字串一次都沒出現。

**照 `format` 寫的客戶端會把整串當成一個 JWT，永遠看不到 disclosure。** 這屬於
「簽章驗得過、語意卻是錯的」那一類，最難被自己的測試抓到。

## A6. VP 用 `context` 而不是 `@context`

**狀態：可以送，但要用更正過的措辭。**

⚠️ **我方原本寫成「JSON-LD 處理會靜默丟掉這些 claim」，那是錯的**——TWDIW 的查驗
端不做 JSON-LD expansion，所以今天沒有東西被丟掉。準確的說法是：這是一個對**會做
expansion 的第三方查驗端**的互通性缺陷，不是一個現行的資料遺失 bug。

值得回報；不值得用我方原本寫的方式回報。

## A7. 持有人 DID 不符 JCS —— **暫緩**

**狀態：不送。** 一個樣本、二手、沒有 App 版本。

在拿到一組標明 build 的 DID 之前不回報。列在這裡是為了讓這個缺口看得見，而不是
默默不提。

## A8. 憑證沒有攜帶任何離線可讀的名稱

**狀態：可以送。**

`vc.type[1]` 是發行系統的內部識別碼（實測 41 字元：
`00000000_demo_drivinglicense_202504251418`）。人類可讀名稱只存在於發行者的線上
metadata（`credential_configurations_supported[…].display[].name`），而且**不在任
何簽章的覆蓋範圍內**。

所以一個離線的皮夾無法告訴持有人他手上這張卡叫什麼。快取也救不了：沒有東西簽它，
顯示快取標籤等於顯示皮夾自己的筆記。

建議：把 display name 放進 VC 本身（`vc.name`，或 SD-JWT VC 的 `vct` 搭配一份有簽
章覆蓋的型別 metadata）。

受害程度排序上它不高——沒有人因此被冒用。但它是這張清單上唯一**每一位持有人、每
一次打開皮夾都會遇到**的。

## 附：一件不是缺陷的事——發行者換不了金鑰

發行者的身分是 `did:key`，金鑰**就是**身分。所以輪替簽章金鑰等於變成另一個發行
者，而所有已發出的憑證的 `iss` 從此不在信任清單裡。皮夾將無法區分「這個發行者被
撤下了」與「它換了金鑰、舊卡其實還是真的」。

**這是唯一一件會讓已經在使用者手上的卡集體變成無法評估的事。** 不是 bug，是設計
的後果，值得在協定層討論而不是當 issue 開。

# B. zkID

## B1. `pk_commit` 的隱藏性是證明端保證的，不是電路保證的

**狀態：可以送。** 這條是做連儂牆時，為了確認一件事而讀電路原始碼順便發現的。

`pkCommit` 是 `userPkLimbs` 加上 `pkBlind` 的 Poseidon hash，而 `pkBlind` 是每次
證明工作階段從 OS RNG 現抽的 31 bytes。現行出貨路徑是安全的
（`mobile/src/lib.rs` 每產一對證明呼叫一次 `random_pk_blind`）。

**但沒有任何約束逼它要新鮮。** `ChunkedPoseidonP256` 自己的註解就寫著
「Hiding: NOT inherently hiding. The caller must include a fresh, random
`pkBlind`」，而電路裡與查驗端都沒有檢查。

一個把 `pkBlind` 釘死的皮夾實作——惡意的，或只是有 bug 的——會**安靜地**把
`pk_commit` 變成一個跨所有 zkID 部署的全域固定識別碼，而查驗方與使用者都無法從證
明本身看出來。

以 SPEC 自己假設的攻擊者（持有整份 MOICA 憑證目錄）來說，這不是理論問題：那個攻
擊者可以對每一個 `userPkLimbs` 重算 `pkCommit` 並比對。

上游的 CLI 對 `--pk-blind` 覆寫**有**警告，所以這個風險是知道的——建議把它從 CLI
的一行警告，升格成協定文件裡明講的部署假設：**「皮夾必須被信任會正確抽樣，而查驗
端無法驗證這件事。」**

### 我方的自我更正，附在這條後面

我原本推論 `pk_commit` **已經是**那個全域識別碼，並照這個推論寫了使用者揭露文案。
讀了電路之後推翻。**高估危害也是寫錯**，文案已改。

把這件事寫在這裡，是因為如果只送 B1 而不說我原本錯在哪，這條讀起來會像是我們早就
知道 blind 的作用——不是的，我們是先猜錯，再去讀原始碼。
