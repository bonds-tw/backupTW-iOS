第一輪盤點在 2026-08-13 開，8 月 17 日結案（原始 42 條、合併 40 條、9 組根因，全數關閉）。
這一輪能看到的東西，第一輪結構上看不到，理由有三個：

1. **有兩塊表面在第一輪之後才長出來。** 能力頁那張「每一張卡值多少」的對照卡
   （`CardCapability.swift`，8/16 建檔，至今只有一個 commit）與整個 `Wall/` 模組
   （8/18 凌晨）都晚於盤點。前者是這個 App 的招牌畫面，後者的每一句失敗文案都已經寫好、翻好、
   有測試，只是還沒有畫面把它畫出來。
2. **這一輪可以審第一輪的修補。** 而修補本身產生了缺陷：`c-18` 加秒數估計時把
   同一個 label 上唯一那句隱私保證蓋掉了；`b-2/b-5` 的重構動了那個 function 的簽章
   卻繞過中間三行 `textColor`；`c-9` 換了封面文案沒有換閘門；`d-6` 的術語收斂
   十一處只改了三處。**四次修補，四次只做了兩半中的一半**，而四次都被記成已關閉。
3. **有些表面第一輪掃到了「同一類缺陷」但沒有列舉到那個畫面。**
   `ZKVerifyViewController` 是唯一一個既沒有亮度提升也沒有 wake lock 的螢幕對螢幕畫面，
   而它是那個要撐過 21.7 秒的。

誠實講規模：**31 條原始發現，全部通過對抗式覆核，合併後 25 條。**
但今天的 Release build 產不出任何一張卡（`CredentialIssuanceAssembly.make()` 非 DEBUG 回 nil）、
也產不出也驗不了任何一份證明（`ZKProofRunAssembly.isSigningAvailable` 同樣的 `#if`），
所以 25 條裡**大約一半在今天的出貨版本上沒有人碰得到**——ZK 查驗頁的綠／橙判定、
藍牙傳送、TWDIW 卡片列、整個牆模組，全部要等簽章那條路接上才會活過來。
這不是折扣，是時間差：**它們會在某一次 commit 之後靜默生效，而沒有任何一支測試會在那一刻轉紅。**

真正今天就會發生在人身上的，最重的是 `2c-1`：出貨版本的使用者唯一真的做得到的動作，
是走進 MyData 把身分證統一編號交出去，而畫面在他按下去之前剛剛承諾過不會發生這件事。

## 二、排序清單

### (a) 會讓櫃檯前的人做錯判定

**2a-1｜能力頁說自己備份的身分證「不帶身分證統一編號」，而那張卡帶著它，出示畫面上還有一個開關**（組 J） — S
現況：`CardCapability.swift:80` 的 `selfIssued.limits` 寫「它不帶身分證統一編號，因為那張憑證裡本來就沒有。」，畫在「**它建立不了的：**」標題底下。這張卡確實帶著它：`VerifiableCredential.swift:225` `claims["unifiedNo"] = model.unifiedNo`；`CredentialIssuance.swift:140` 沒有統編**根本發不出這張卡**；`PresentCredentialViewController.swift:423` `cannotBeWithheld = ["name"]`，統一編號走 `:365` 的 `disclosureRow`，是一個可勾的開關；勾了就進 `OfflineVerifier.swift:1358` 的 `claimDisplayOrder`，出現在里長螢幕上、列在已驗簽的欄位裡。
理由那半是對的、而且是量過的（`IssuerCertificate.swift:462-472`：真實 MOICA G3 憑證的 Subject DN 只有 C／CN／serialNumber，掃過位元組沒有 `[A-Z][0-9]{9}`；`DistinguishedNameTests.swift:190-205` 釘住 serialNumber 不是統編）。**一句關於「憑證」的真話被寫成一句關於「這張卡」的話。**
建議：改成事實——「它帶著你的身分證統一編號，但那是一個你每次出示都可以關掉的欄位；關掉之後查驗方只會看到一個打不開的承諾。」`CardCapabilityTests` 目前沒有任何一條抓得到 limits 說謊，值得補一條把 `selfIssued.limits` 跟 `VerifiableCredential.nationalIDClaims` 的鍵對起來。
判準 (a) — 錯誤的方向是「比實際更安全」，落在整個 App 唯一一頁承諾誠實列出限制的畫面上，而且講的正好是統一編號。這跟隔壁 `WallDisclosure.countIsSignaturesNotPeople` 特地改掉的錯誤是同一個形狀（把一個選擇寫成一個做不到），只是方向相反。

**2a-2｜ZK 查驗把寄件方自己附的但書清單原樣印出來，空清單就是一片乾淨的綠**（組 O） — M
現況：`ZKProofPackage.swift:96` `let caveats: [ProofCaveat]` 是一個普通的解碼欄位；`validate()`（:176-188）只檢查 `version` 與四個 artifact 的名稱與大小，**從不檢查 `ProofCaveat.unconditional` 在不在裡面**。`ZKPackageVerifier.swift:147/155` 兩處都是 `caveats: package.caveats` 直接穿過去。`ZKVerifyViewController.swift:275-278` `guard !messages.isEmpty else { caveatContainer.isHidden = true; return }`，而 :538-543 的綠色判定是從 `verdict.accepted` 來的、與這份清單無關。把 `.zkproof` 的 JSON 裡 `"caveats"` 改成 `[]`，四個二進位檔一個位元組都不用動，出來就是全畫面最大的一行綠字，底下什麼都沒有——那六句「不論查得多仔細都建立不了的事」（簽章材料可永久重播、內政部知道統編、去重編號每個查驗方相同、有效期未證明、撤銷根未錨定）一句都不在螢幕上。
這個 App 自己在生產端擋過同一件事：`ZKProofRunReport.swift:93-94` 算 `omittedUnconditionalCaveats` 並印「!! CAVEAT LIST INCOMPLETE」，理由就是那個陣列任何呼叫者都構造得出來；憑證那條路也沒有這個問題——`OfflineVerifier.swift:981-1002` 的 `VerificationCaveat` 是查驗端自己組的。**只有 ZK 這條路，構造者是陌生人。**
建議：`validate()` 拒絕一份 `caveats` 不含它宣告的 `version` 當時所有 `unconditional` 成員的 package（v1 五條、v2 六條）——**拒絕比補回來對**，一份對自己的限制說謊的檔案不該被畫出來。若判定太嚴，退而求其次在 `ZKPackageVerifier.swift:147/155` 取
`Set(ProofCaveat.unconditional).union(package.caveats)`，一行，而且順便正確升級 v1。測試照 `ZKProofPackageTests.refusesAnUnknownCaveat` 的形狀，把 JSON 的 `caveats` 改成 `[]`。
判準 (a) — 缺哪幾條是攻擊者選的，而最值得先拿掉的那條正是「(cert, signed_response) 可以在你不在場的情況下永遠鑄造新證明」。剩下的是一行綠字。比空清單更難發現的是只拿掉兩條：標題還在、四個項目還在，沒有任何訊號說少了兩條。

**2a-3｜藍牙收完一份證明之後，配對碼還在畫面上、電台已經關掉，而它下面掛著上一個人的判定**（組 L） — M
現況：`ZKVerifyViewController.swift:387-390`，`.finished` 第一件事是 `stopLink()`（`link?.stop(); link = nil`）。而 `beginEngagement()`——鑄識別碼、畫 QR、開電台——全 repo 只有一個呼叫點：`viewWillAppear`（:127-130）。`verify(package:)`／`present(_:package:)`／`show(...)` 沒有任何一個重開；`codeImageView.isHidden` 只在 `beginEngagement` 內被寫（:327/:337）；文件選擇器是 sheet，不會再觸發 `viewWillAppear`。
這個畫面自己的註解把被違反的兩條都寫出來了：:310-315「沒有掃描器在跑的碼，是一個被掃了也不會有事的碼……`engagement` 存在就是為了讓兩者不會分岔」——而 `engagement` 只在 :318 被寫、`stopLink()` 只碰 `link`，分岔之後沒有任何東西讀那一對；:298-300「有判定之後不收起 QR，是因為收起來這個畫面就沒辦法接著查下一個人，而櫃檯前的人不只查一個」——那個「接著查下一個」對藍牙這條路是假的。
第二個人上來掃還在畫面上的碼，他的手機廣播進一個沒有人在聽的房間，停在「已就緒——等待查驗方的手機。」（`BluetoothLink` 沒有廣播逾時，只有傳完之後的 1.5 秒 acknowledgement），里長的螢幕零像素變化：`liftTheVerdictAboveTheFold()` 剛把上一個人的綠色「通過」搬到最上面，底下寫著「已透過藍牙收到 389 KB。」，而畫面上任何地方都沒有時間戳（只有「花了 %.1f 秒」，那是時距）。
憑證那條路沒事，而且是靠運氣：`VerifierViewController` 的判定是 **push** 出去的結果頁（:745-753），返回時 `viewWillAppear → beginCheck() → startLink(for:)` 順手重開。ZK 這一頁的判定畫在原地，永遠不會離開，所以永遠拿不到那個副作用。
建議：判定畫完之後（不是之前，免得傳輸中換識別碼）重新 `beginEngagement()`；**新碼上去的同時 `statusLabel`／`detailLabel`／`caveatContainer` 必須一起清掉**——活著的配對碼跟上一個人的判定不可以同時在畫面上。測試可以直接釘那一對：`receiveOverLink(.finished(...))` 完成後 `link != nil` 若且唯若 `codeImageView.isHidden == false`，也就是那段註解宣稱不可能發生的分岔。
判準 (a) — 一行沒有改變的綠色「通過」，站在全畫面最大的位置，而第二個人的手機正在說「已就緒、等待」。順帶：解碼失敗那條路（:399-400）也先跑了 `stopLink()`，所以一份從來沒被判定過的證明也會把電台永久關掉。

**2a-4｜出示畫面上一次擦到邊緣的返回手勢會永久殺掉藍牙傳送，輪播卻重新開始，藍牙那行凍在最後一句話**（組 L） — M
現況：`PresentCredentialViewController.swift:171-190`，`.startShowing` 做 `brightness.raise(); wakeLock.hold(); startCarousel()`，`.stopShowing` 做 `stopCarousel(); stopLink(); …`。而 peripheral 只在 `renderFrames` 裡被建立（:659-671），`render()` 有四個呼叫點、**沒有一個在出現路徑上**；`viewWillAppear`（:161-164）只跑 `apply(lifecycle.willAppear())`，`PresentationScreenLifecycle.willAppear`（:1103-1107）回 `.startShowing`。所以「開始擦、放掉」＝ `viewWillDisappear` 然後 `viewWillAppear`：輪播從第 0 張重來、亮度回滿，`CBPeripheralManager` 已經被釋放而且**再也不會被重建**。`BluetoothLink.swift:126-131` 的 `stop()` 不發 `onState`，所以 `linkLabel` 停在最後一句——實際會凍住的是「正在開啟藍牙…」／「已可透過藍牙被搜尋到…」／「透過藍牙傳送… N%」。
這個畫面的註解（:151-159）描述的正是這個握法——「單手、手臂伸直、舉在別人的相機前，那正好是會擦到左邊緣的握法」——並列舉了取消的返回會弄壞什麼：凍住的碼、過期的「第 2／3 張」、還在等的收集器。**電台不在那張清單上。**
查驗端這時看到的是「連線在整份證件送達前就結束了。」——如果它已經連上；還沒連上的話 `didDisconnectPeripheral` 因為 `collector.progress == nil` **一句話都不會說**，而廣播已經永久消失、central 又沒有掃描逾時，於是他對著一個安靜的畫面掃到底。
建議：把 peripheral 的壽命搬到 `PresentationScreenLifecycle` 的 effect 上——`.startShowing` 起、`.stopShowing` 停（`stopLink()` 本來就在那裡），`serviceID` 與 `presentationPayload` 留在 controller 上讓 effect 拿得到。兩半就能互相對讀，跟 `VerifierScreenLifecycle` 一樣。最低限度：連線在沒傳完的情況下被拆掉時，`linkLabel` 不可以繼續宣稱傳輸進行中。
判準 (a) — 一個人被告知傳送失敗、另一個人被告知還在進行，而唯一還活著的是他們本來要避開的慢路。`PresentationScreenLifecycleTests.swift:36-43` 已經有這個「擦到又放掉」的案例，但它只斷言回傳的 enum，不斷言電台，所以永遠是綠的。

**2a-5｜橙色在 ZK 查驗頁是「拒絕」，在這個 App 其他每一個地方是「這不是對任何人的判斷」**（組 K） — S
現況：`ZKVerifyViewController.swift:253` `case .some(false): statusLabel.textColor = .systemOrange`，由 :538-540「這支手機查了這份證明，不接受」驅動。對照全 App：`VerifierViewController.swift:896-897` 真正的拒絕是 `PresentationUI.verdict("⛔️", "查驗未通過", .systemRed)`；:913-918 把橙色留給「沒有東西被查驗」，上面的註解寫著「**不是壞狀態的狀態，不可以畫成壞狀態**」；`HomeViewController.swift:114-118` 用橙色標過期卡，理由是「過期是關於一個日期的事實，不是任何人的過錯」；`CapabilityViewController.swift:244` 用橙色標 `.partial`。
里長剛在憑證那一頁學會紅＝拒絕、橙＝我這支手機沒東西可查、不是對方的問題，轉頭查一份證明拿到橙色，讀成「無法判定，這台裝置答不出來」——而那是**同一個畫面上真的存在、另外畫的一個狀態**（`verdict: nil`、黑字、「無法判定」）。實際上那份證明是被拒絕的。這是第一輪 `a-3` 的鏡像：`a-3` 把家務事畫成指控，這一條把指控畫成家務事。
（誠實補充：`DiagnosticsViewController.swift:84` 與 `ZKProofViewController.swift:841` 也用橙色三角標自我檢查失敗，但那兩處判的是使用者自己的裝置，不是對面那個人。）
建議：沿用憑證端那套三分法——⛔️／`.systemRed` 給 `accepted == false`，⚠️／`.systemOrange` 只給 `verdict: nil`，✅／`.systemGreen` 給通過；跟 `2b-2` 同一次改，因為都是改用 `PresentationUI.verdict`。測試斷言「被拒絕的證明與被拒絕的出示拿到同一個顏色」。
判準 (a) — 錯的方向是把過錯從證明搬到裝置上，也就是往「更好看」那一邊；而承載這個區分的字，正好是全畫面最難讀的那一行（見 `2b-2`）。

**2a-6｜查驗方自己的時鐘不對，被畫成 ⛔️「查驗未通過」，而唯一講得出真正原因的兩句話被丟掉了** — M

覆核比原始發現更強：**編譯進去的主機解得出來。**`WallConfiguration.swift:39` 是 `https://bonds.tw/api/wall`，`dig` 有 A record。所以在任何出貨版本上，「這個版本的位址設定」**結構上不可能**產生 `.cannotFindHost`——這個分支唯一的到達方式是使用者那側的 DNS 失敗，而那句話斷言的正是程式已經排除的那個解釋。出處也查得到：`docs/wall-signing-plan.md:422-423` 把「404／DNS 失敗」併成一桶並寫下這句話，當時編譯進去的主機是不存在的 `wall.bonds.tw`（那時它是真的）；§七在 `e68cc31` 把主機定成 `bonds.tw`，十五分鐘後 `1f047e0` 寫 `WallCopy.swift` 時把定案前的句子原封帶了進來。它以為自己在描述的那個 404，其實走去別的地方（JSON 404 → `.unavailable`，非 JSON 404 → `.unknownWhetherPublished`）。

（誠實界定：`Wall/` 現在只有型別與測試，沒有 client 也沒有畫面，`WallSigning` 零個實作，所以這句話還沒有到過任何人眼前。captive portal 也是最弱的實例（多數會劫持 DNS，落到 `.unreadableReply`）；紮實的實例是單純的 DNS 失敗——壞掉的 resolver、DNS 死掉的 VPN、ISP 層的 DNS 阻擋，也就是這個 App 的讀者。另外「註解說 None hard-codes a label」那一腿是誇大的：那句話針對的是硬寫**非 nil** 標籤的分支，硬壓成 nil 在這個檔案裡是既有的編輯判斷，有六個。）
建議：body 只講確定的事（「什麼都沒有送出去」），原因留兩種可能（這個版本的位址設定，或這個網路解析不到名稱），`retryLabel` 照 `retryCost` 走——`.resend` 本來就該有那顆鍵，而且那句「同一份證明可以再送一次」要補回來。

## 三、建議先做的三件

**第一件：`2c-1`，單獨一條，先於其他所有。**
它是這份清單裡唯一一條**今天的出貨版本上有人真的會碰到、而且有代價**的缺陷，代價是身分證統一編號加一整份戶籍謄本，換回來的是零（`save` 在 `issue` 之後，Release 到不了）。修法是兩行，而且形狀已經在同一個 commit 的隔壁寫好了（`ZKProofViewController.swift:370-380`）。要補的測試斷言的是性質不是字串：`isAvailable == false` 時不存在任何可觸發 `MyDataWebViewController` 的啟用控制項。**第一輪已經寫對過這個建議，實作只做了兩半中的一半，所以這次要釘的是那條缺陷的形狀本身——文案與行為各自為政。**

**第二件：組 J 六條，也就是把能力頁盤點一次（`2a-1`、`2a-7`、`2b-1`、`2b-4`、`2c-8`、`2d-3`）。**
六條全部落在 `CardCapability.swift`（117 行、一個 commit、從沒被任何一輪盤點讀過）與 `PresentationScenario.swift`／`CapabilityViewController.swift`，改動量互相重疊：`2a-1` 與 `2b-1` 是兩張卡的同一種錯（把一句關於別的東西的真話寫成關於這張卡的話）；`2a-7` 與 `2c-8` 是判定那一格的兩個問題（一個是文案該降級、一個是它根本不看 build）；`2b-4` 是版面。**這一頁是這個 App 的招牌，也是唯一一頁把「不誇大」寫成自己存在理由的畫面，而它現在有三條往「比實際更安全／更確定」的方向說謊。**四條測試就能把它釘住：`proves` 不得出現現在式的「持有／有效」、`selfIssued.limits` 對得上 `nationalIDClaims`、非 DEBUG 時沒有 scenario 是 `.supported`、每張卡至少宣告一條撤銷／有效期限制。

**第三件：`ZKVerifyViewController` 把第一輪那次重構做完（`2b-2`、`2a-5`、`2b-5`），順手 `2a-3` 與 `2c-2`。**

## 四、已排除的四條

覆核階段推翻了四條，記在這裡是為了不要有人第三次去審同一段程式碼。最值得記的三條：

1. **「揭露畫面最重的一句說『沒有勾的欄位不會送出』，而姓名不是可勾的欄位、且一定送出」——推翻。**
   這條的承重主張是「App 唯一一句講對姓名的話在能力頁上，不在做決定的那一頁」。它是假的：那句話就在做決定的那一頁，開關清單下面一行，而且是全墨畫的。這條的價值在於它**證明了正確的做法已經在那裡**——`2b-1` 與 `2a-1` 的修法就是把同一句話補到能力頁上，而不是反過來。

2. **「能力頁的顏色訊號實測 1.12:1，所以三個訊號其實只有兩個」——推翻。**
   證據大致正確，結論建立在數錯上（那三個訊號是符號／標題／顏色，而符號與標題都是全墨且各自獨立成立），而且這條發現自己就承認沒有人會因此被誤導。留下來的真問題是 `2b-4` 的容器邊界，那是另一件事。

3. **「『這個證明無法顯示同一個身分是否已經在別處用過』把離線環境的限制講成證明本身的無能」——推翻。**
   引文逐字正確，但註解被讀反了（`ZKProver.swift:501-506` 講的正是相反的事），而且它要求的補救**已經上線、就在那句話旁邊**。這一條是這輪唯一一個「盤點者比程式碼晚一步」的例子，跟 `2d-4`（程式碼比盤點紀錄晚一步）剛好對稱。

第四條是 `2d-1` 的另一個版本，以「今天沒有人碰得到」被推翻——同一個缺陷以誠實標註可及性的形式活了下來，就是 `2d-1`。**這兩者的差別值得記住：可及性是 band 的參數，不是真偽的參數。**

## 五、明確不建議做的

1. **不要因為「今天沒有人碰得到」就把 `Wall/`、TWDIW、與 ZK 那幾條往後排到功能上線之後。** 這是本輪最重要的一條程序建議。那些字串已經寫好、翻好、有測試綁著，而它們會在某一次 commit 之後**靜默生效**——沒有任何測試會在那一刻轉紅（`2d-1` 尤其：它會從 (d) 直接跳到 (a)）。現在改是一行文案，上線之後改是一次事故。

2. **`2c-1` 的修法不可以是「拿掉『因此不會去抓』那句話」。** 句子是對的，按鈕是錯的。這個方向的誘惑很大，因為刪一行比加一個 guard 快，而結果是把一個誠實的畫面換成一個沉默的畫面。

3. **`2a-7`／`2b-1` 不可以靠「加一條但書」解決。** 但書那一塊的框架是「就算通過了，以下仍然成立」——那說的是**相容**，不是「這一半沒答到」。`ScenarioSupport.partial(actually:)` 這個 case 就是為了後者存在的，而且已經用在兩個落差更小的請求上。在綠勾底下加但書等於承認落差又保留誇大。

4. **`2a-2` 不可以只做「照樣顯示寄件方給的清單，再加一句警語」。** 拒絕（`validate()` 檢查完整性）或補齊（`union(ProofCaveat.unconditional)`）二選一都可以，但不可以留下一條「這份清單由寄件方提供」的註腳就算數——那把一個可以在程式裡消滅的問題，轉包給櫃檯前那個沒有能力查證的人。

5. **`2b-2` 不可以就地把 `.systemOrange` 改成 `.systemRed` 了事。** 那會留下**第三套**判定樣式（憑證是彩色底＋全墨＋符號、ZK 變成彩色文字＋紅、Diagnostics 又是另一套），而 `PresentationUI.verdict` 存在的理由就是不要有第二套。顏色要跟符號、對比、VoiceOver 一起搬。

6. **`2c-6` 壓下配對 QR 時，不可以連檔案選擇一起關掉。** 檔案那條路會在本機誠實地、免費地失敗；該關掉的只有那個**要對面的人花 21.7 秒與一份自己的身分證明**的邀請。這跟第一輪第 5 條（「不要為了拿不到查驗檔案就把首頁那一列藏起來」）不衝突：藏起來的不是一項能力，是一個對別人開的支票。

7. **`2b-3` 的註解不可以用「刪掉」來修。** 註解在對的位置、對的理由，錯的只有數字；而且 `footnote` 與 `body` 要同一次改完，否則兩層階層會被洗成同一層或第二次反轉——這是第一輪第 9 條的原話，本輪它自己又應驗了一次。

8. **`2a-3` 不可以用「有判定就收起配對碼」來修。** 第一輪已經否決過隱藏（櫃檯前的人不只查一個），而且問題根本不是碼還在，是**碼還在而電台不在、上一個人的判定還在**。正解是重新開機（re-arm）＋在新碼上去的同一刻清掉上一個人的畫面，並且把那一對寫成測試斷言。

9. **不要把本輪任何一條的修補紀錄寫成「已關閉」而不附驗收證據。** 本輪 25 條裡有 5 條的存在理由就是第一輪的修補紀錄比實際做的多——`c-9` 只改了文案、`b-2/b-5` 繞過了 `textColor`、`b-4` 只做了地板、`d-6` 十一處改三處、`c-18` 順手蓋掉一句話。**五次裡沒有一次是判斷錯誤，全部是「兩件事寫在一起、只做了一件」。**下一次的驗收欄位應該逐項對回建議裡的每一個分號。
