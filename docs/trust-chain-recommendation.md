## 一、應該改變設計的發現

### 1.1 承諾值現在可以碰撞，而且不需要密碼學、不需要 GPU、不需要金鑰

`TrustList.swift` 第 112–126 行用 `\t` 接欄位、用 `\n` 接行，`validate()` 只檢查版本、非空、id 不重複。沒有任何地方拒絕欄位內部出現 `\t` 或 `\n`，也沒有把 entry 筆數放進摘要。所以一則 `note` 就能整行偽造：

```
A = 一筆 entry，note = "MOICA G3\nzzz-mirror\tmirror\t內政部憑證管理中心（緊急換發）\t依§5.2 啟用"
B = 兩筆 entry，第二筆是 zzz-mirror（mirror）
```

兩者的 `canonicalForm` 逐位元組相同，`commitment` 都是
`fd03501d0dfe03351dffb9de3ca55af543b412cf2781a5805a29b95a6de185b3`。
`A.trusts("zzz-mirror")` 是 false，`B.trusts("zzz-mirror")` 是 true，兩份都通過 `validate(expectedCommitment:)`。20 行 Python 可重現。

`note` 是設計上刻意開放給人寫的欄位（「Why this issuer is on the list… so that a list which has grown over time can be audited by reading it」），也就是最容易透過一次 pull request 影響的欄位。`publishedAt` 是第二個注入點，而且沒有人把它當成承載信任的欄位在審。

這比第一版擔心的摘要研磨嚴重得多：研磨頭尾 8 碼是 32 bit 的 GPU 工作，注入是零成本的精確碰撞。而且它同時打穿四個選項——A 的內建常數、B 的門檻簽章、C 的十一萬份紙本、D 的接續鏈，全部承諾在同一個字串上。**在非單射的編碼上公開一個承諾值，比什麼都不出還糟**：它製造一份長期、廣泛發佈、而且審過的人讀到的意思跟機器讀到的不同的證言。

現有測試（`renamingAnIssuerChangesTheCommitment`、`promotingAMirrorChangesTheCommitment`）測的是「特定的改動會改變摘要」，從來沒測「不同的清單不能共用一個摘要」。缺的是把 `canonicalForm` 反解回 entries 並要求往返相等的性質測試。單射性才是安全性質。

### 1.2 未簽名的摘要是對的，但 eIDAS 的另一半——裝置能自己走的接續鏈——第一版就必須進去

`TrustList.swift` 第 41–47 行的推理（簽章會逼出「誰簽的」這個在憲政危機中沒人能事先同意的問題）不是簽章的次等替代品，它就是全世界最大宗信任清單系統的根設計：ETSI TS 119 612 Annex A.1 用標準文體講同一個問題，eIDAS 的答案是把 SHA-256 十六進位印在官方公報上。台灣自己的根 CA 也規定同一個形狀——GRCA CPS v2.0.1 §6.1.4 列了四種把根公鑰交給依賴方的管道，第 (4) 種就是透過媒體公告金鑰啟用見證書。這段註解應該停止遲疑、開始引用。

第一版沒抓到的是那個系統的**另一半**：報紙摘要只錨定一次，之後的每一步都靠裝置自己能走的簽章鏈——每一份 pivot LOTL 由前一份指名的金鑰簽署。一台釘在 2019 年報紙、從此離線的裝置，只要拿得到檔案（隨身碟、QR、快遞、人肉），就能走到今天的信任狀態，全程對網路零信任。

`TrustList` 現在完全沒有接續機制。`version: Int` 是一個沒有人拿去跟任何東西比的數字，沒有 `supersedes`、沒有指名的下一個簽章者、沒有回滾規則、沒有單調性。後果是結構性的：**清單永遠只能跟 App binary 一樣新，而 binary 的真正信任根是 Apple 的程式碼簽章加上 App Store 可達性——兩者都不是台灣的、封鎖時也都不在**。

所以承諾值要錨定的是一條**鏈**，不是一個**值**。第 26 行那句「an on-chain root」的期待請刪掉，理由見 §6。

### 1.3 手抄的十六進位是事後的爭議解決工具，不是櫃檯儀式

十六進位是六種表示法裡最差的（1047 人受測，10.44% 的針對性攻擊沒被發現，分段沒有統計顯著差異）；愈長愈糟（20/40/60 位數的誤接受率 13.2% → 30.9% → 43.5%）；只差一個字元時 60.25% 的人會接受；給一個「標記為已驗證」的開關，20 人中 12 人沒比對就按下去、18 人相信自己驗過了。基準線是 Chrome SSL 警告 70.2% 的點穿率——而那裡的替代方案只是「我想看的網頁」，這裡的替代方案是「我認識這個人」，只會更差。

結論維持，但第一版自己違反了它：**驗證畫面上不能出現任何承諾值**，8 碼也不行。它在櫃檯上唯一的功能是看起來很官方，而且旁邊沒有任何可比對的東西。承諾值的正確位置是 `backupTW/Diagnostics/SelfCheck.swift` 的 `.informational` 列——兩個工程師拿著 terminal 事後對帳時會去的地方。手抄得出來的正規形式要保留，它對跨實作驗證與事後爭議是真的有價值；只是永遠不要拿到里長面前。

### 1.4 一條該寫進設計的規則：加信任要門檻，減信任不要門檻

這條是三份審查互相衝突後留下來的東西。審查者三說「沒有人力時遺失比竊取更可能，所以 1-of-2」；審查者一說「對手的第一步是抓保管人，所以 n=1 不可行」。兩邊都對，但它們講的是**不同的權限**。

- **增加信任**（新增簽發者、換發鏡像）必須有門檻 k ≥ 2，且保管人跨司法管轄區。一個被脅迫的人不能新增簽發者。
- **減少信任**（降級、撤銷、終止整條鏈）門檻是 1-of-N，而且刻意做得便宜。它被濫用的最壞結果是裝置退回今天的行為——只信內建錨、拒絕第三方簽發者——那是安全的。

這條規則同時解掉審查者三的可用性焦慮（減信任永遠可用，不會因為兩個人失聯就卡住）和審查者一的脅迫攻擊（加信任需要兩個管轄區的兩個人同時被拿下）。如果只招得到兩個保管人，誠實的做法**不是**降到 1-of-2，而是不要出加信任的權限——只出 A 加終止金鑰。

## 二、這是在防哪一種失敗

**沒有簽發者是基準案，尺度是週。** 馬祖兩次斷纜後約 50 天連不上；烏克蘭司法部的民事、法人、不動產登記在 2024-12-19 攻擊後約 32 天不可用（完整主權、沒有被佔領、有國際支援），不動產登記最後才在 2025-01-20 回來；台灣自 2023 年起至少 11 次海纜受損事件。門檻其實遠低於這些：GRCA CPS §4.9.10 要求依賴方使用憑證前查 CARL 或 OCSP，§4.9.7 把 CARL 有效期壓在 36 小時——**任何合規的台灣驗證方在失去訊號 36 小時後就失效**，遠早於任何戲劇性的事發生。設計視野是週，不是小時。白皮書應該主動寫出這條不合規，不要等審查者找出來；同時註明 §1.4.2 禁止用於軍令戰情——那份 CP 起草時眼裡沒有武裝緊急狀態，所以它回答不了 backupTW 的問題。

**敵意簽發者是真的，但它的形狀不是 `isMirror` 當初設想的那個。** 兩個最接近的政治先例裡，對手都沒有拿到合法簽發者的私鑰：俄羅斯**自己立了一個簽發者**，並讓承認它成為生存條件（四州到 2023 年 5 月約 150 萬本護照，拒絕者的人道援助、撤離、水電、補貼燃料被延遲或拒絕）；香港用**自己真實的金鑰**對付自己人（2024-12-24 撤銷 7 人護照，2025 年 8 月再 12 人），沒有任何密碼學被攻破。PRC 對台版本的預置早就存在：台灣居民居住證，2018 年 9 月起發。

所以真實的敵意事件是**對手要求你承認它自己的簽發者**，或**合法簽發者撤銷它不想要的人**。金鑰竊取是三者中最不可能、也是唯一能靠防偽解決的那一個。這件事把優先順序倒過來：**一個能接受鏡像簽發者的能力，按這些先例，被對手行使的機率至少不低於被流亡政府行使的機率。** 只能加、不能減的 `TrustList` 送進一個權威已被接管的情境，是送禮。分辨機制不是那個旗標，是釘住的錨加上「把一個密碼學上完全正確的簽發者降級」的能力。DigiNotar、CNNIC、哈薩克都是靠推給依賴方軟體的信任庫更新收拾的，離線沒有對應物——這正是降級必須**預先載入並且被正面指名**、而不是臨時抓取的原因。

**新增的第三條：對手的第一步是抓人，不是解密。** 在憲法約束的前提下，對手可以在台灣境內脅迫個人。bonds-tw 的貢獻者名字在公開 commit、白皮書、研討會議程上。所以任何「一把金鑰、一個人、境內、保險箱」的設計在這個威脅模型下不是節省成本，是把 MOICA 換成一個更軟的目標，然後附贈一個綠色打勾拿去洗白。第一版在 §3 把這寫成殘餘風險，又在 §4 用營運成本選了它——這是錯的，改掉。

**新增的第四條，而且它比密碼學重要：涵蓋率才是主導風險。** MOICA 自己的計數器 2026-08-12 顯示累計發出 11,262,958 張，人口約 2340 萬；回報的有效數約 347 萬張實體加 71 萬張行動。也就是說能被驗的人的天花板大約是人口的 15–18%。

這裡要修正審查者一的機制描述：那個數字約束的是「誰曾經能把憑證灌進 App」，不是「誰在櫃檯前能通過驗證」——卡片路徑的憑證有效期與撤銷在驗證時仍會被檢查，所以兩者的上限差不多，**結論不變**。櫃檯前最常見的結果就是「無法驗證」。第一版把這當成 UI 語氣問題，那是錯的：這是安全問題，因為 App 的下面永遠有一個免費、即時、隨時可用的替代方案——「我認識這個人」。每一次沒有下一步的拒絕，都是在推里長不要再打開這個 App；而一個沒人打開的 App，A、B、C、D 四個選項的分數一模一樣，都是零。

**最後一條，關不掉：對手可以完全不理會你的 App。** 驗證是純本機操作，所以對手可以發自己的驗證器和自己的證件，並讓出示它成為拿到暖氣、燃料、撤離名額的條件。這就是赫爾松。backupTW 對此無能為力，白皮書要把這句話直接寫出來（見 §8）。

## 三、四個選項

每個選項都要寫明**螢幕上可以誠實地說什麼**，因為那是殺掉大部分漂亮設計的約束。

### 基準線（今天）

`IssuerCertificate.swift` 釘一個 MOICA G3 錨，所有第三方簽發者一律拒絕。螢幕可以說：這份文件是出示者本人簽的，簽章與挑戰都對得上。永久安全、離線、零營運成本。完全做不到 §5.2。

### A — 內建**一個**承諾值

**不需要任何持續運作的組織。**

`TrustList` 加 `static let pinnedCommitment: String`，用 `IssuerCertificate.swift` 頂端那種來源區塊寫清楚它怎麼來的、能證明什麼、不能證明什麼。清單檔案隨 bundle 出貨。裝置只在承諾值等於這個常數時接受一份清單，任何傳輸管道都行。

**只釘一個，不是兩個。** 第一版抄了 OJ C/2026/1944 §2.1 的雙錨讓步，但 eIDAS 的雙錨是**鏈走訪的兩個入口**，後面的環節會取代前面的；一個裸的雙值接受集合在全新安裝的裝置上沒有這個順序關係。而 §6 已經確立新清單的重點是**降級**，所以前一代那份就是還信任著已被降級的那個簽發者的清單，而且它是公開檔案。重灌、還原備份、換手機的裝置沒有歷史高水位，兩個都會照收——那是內建的降級管道。既然 D 的鏈走訪這一版就出，第二個釘子沒有存在的必要。

**存活：** 網路消失（永久）。任何管道丟進手機的偽造清單。靜默改標籤（`displayName`、`note` 已在摘要內）。被接管的 MOICA 想把自己加成鏡像（它改不了編譯進去的常數）。
**不存活：** App Store 不可達——封鎖時它就是不可達。輪替故事是「發一版 App」，而這個 repo 15 個月零個 release tag。它也繼承上一層那個未關的 TODO：如果編譯時釘錯了，底下全錯。
**櫃檯負擔：** 零。
**螢幕可以說：** 「簽發者：<名稱>（不是內政部）。依這支手機內建的信任清單判斷，清單發佈於 2026-08-09，距今 187 天。」

### D — 每一版清單預先指名下一版的簽章金鑰（門檻式）

**不需要常設組織、不需要開會，而且它會輪替。這是小專案唯一負擔得起、又真的能換發的選項。**

規則直接取自 did:webvh：這一版的更新金鑰，其雜湊必須出現在上一版的 `nextKeys` 裡。

1. v1 隨 binary 出貨，正規形式內含 `nextKeys{threshold: 2, hashes: [H(pk_a), H(pk_b), H(pk_c)]}` 與 `killKeys[…]`。它的承諾值照 A 釘死。
2. 要換清單時，兩位保管人各簽 v2，發佈 `(list₂, pubkeys, sigs)`。v2 內含下一輪的 `nextKeys`。
3. 持有 v1 的裝置從**任何**管道收到那些位元組——最有用的是從持有人的手機——先用 v1 已知的雜湊比對公鑰，**先驗簽章（簽在收到的原始位元組上）**，才解析 JSON，再檢查 `sequence` 嚴格遞增，然後採用 v2。之後它就知道下一輪的 `nextKeys`，繼續走。
4. 每一輪的私鑰離線產生、用一次、銷毀。被攻破的窗口是一輪，不是整條鏈的壽命。

**這不是對第 41–47 行那段推理的讓步，是把它解掉。**「誰簽的」變成「你已經信任的那份清單事先指名的那些人簽的」——而**那個**問題可以在承平時期、在任何人被拿下之前，事先談定。過程中不諮詢任何常設權威，不抓取任何東西。

**簽章覆蓋的是收到的原始位元組**，這一點是對審查者一「傳輸摘要」建議的修正：後繼清單的位元組不可能被前一版預先承諾（前一版還不知道它們），所以預先承諾傳輸摘要在數學上做不到。能做到的是**先驗簽章再解析**。於是變成**兩個摘要、兩份工作**：簽章對原始位元組，供機器在解析前完成認證；正規形式承諾值對語意，供人與跨實作事後對帳。

**門檻與管轄區：** `nextKeys` 是資料不是程式碼，門檻寫在清單裡。建議 2-of-3、至少一位在 ROC 管轄之外、**第一輪就要如此**，而不是「以後再說」。這跟第一版加在 B 身上的招募前提是同一個前提；第一版沒把它加在 D 身上，那個不對稱就是錯誤。招不到三個人時，出 A 加終止金鑰，不要出 1-of-2。

**終止金鑰（kill keys）：** 1-of-N，簽一則固定短訊息，效果是這台裝置永久拒絕所有第三方簽發者、停止走鏈、退回內建錨。它唯一的權力是**減**，所以被偷的最壞結果是把功能打回今天的行為。觀察到分叉（同一個 `sequence` 出現兩份都正確簽署但承諾值不同的清單）等同終止事件——裝置不去裁決哪一份是真的，它熄燈。

**存活：** 網路消失。App Store 不可達（鏈搭持有人的手機走，抽屜裡放兩年的裝置可以從冷啟動往前走完，全程沒有網路）。被接管的 MOICA。偽造清單。回滾。一位保管人被脅迫或失聯。
**不存活：** k 位保管人同時被脅迫（見 §8）。扣留（見 §8）。而且它授權的是**變更**，不是**正當性**：它說的是「當初把這條鏈架起來的那群人事先打算讓這一版生效」，那是一個真實的主張，但它不是「這個鏡像簽發者是合法政府」。螢幕上就要這樣講。
**櫃檯負擔：** 零。持有人負擔：帶一個檔案。
**螢幕可以說：** 「這份清單是第 3 版，這支手機從 App 內建的第 1 版一路核對過來，每一版都由前一版事先指名的金鑰簽的。發佈於 2027-02-11，距今 34 天。這支手機沒有連網，無法確認第 3 版是不是最新的一版。」

### B — 具名公民團體的門檻背書

**D 的目的地，不是 D 的替代品。**

技術上，B 就是 D 把 `nextKeys` 的持有者換成具名的公開組織、門檻調高。線路格式一樣、驗證程式碼一樣、螢幕詞彙一樣。真正的差別只有一個：**螢幕上敢不敢說出是誰**。D 的保管人是專案自己的人，畫面上說不出名字；B 的背書者是具名、多元、部分在境外的團體，名字可以印出來。

這也定義了切換條件，而它不是技術條件：

> 當三個以上的組織、其中至少一個在 ROC 管轄之外，**以書面**同意持有金鑰並被具名寫進一個開源 binary 作為戰時信任錨時，才切到 B。

在那之前不要。名單上放沒有同意過的組織，比沒有名單更糟，因為它在螢幕上寫下程式碼兌現不了的名字。多元性才是安全性質，不是數量：全部由台灣境內團體組成的門檻，是加了步驟的單點故障——一道戒嚴令或一次封鎖同時碰到全部。

**招募要寫進書面的東西，不只是同意持有金鑰**（這是第一版漏掉的）：簽署演練的頻率，以及一條**不需要湊到門檻就能執行的金鑰退場路徑**。三年之內這些團體會換人、掉金鑰、被併購、或安靜地不做了；2-of-3 容許掉一個，掉第二個就永久無法更新，而如果金鑰之間從不運動，沒有人會發現，直到緊急狀態那天。Sigsum 的見證者是持續簽署所以已知存活；一個 18 個月簽一次的門檻，是套著同一份安全性證明的另一個系統。

**螢幕可以說：**「這位簽發者在一份由 <組織甲>、<組織乙>、<組織丙> 背書的清單上。」——名字，不是「5 個裡的 3 個」。一個里長沒辦法在櫃檯前評估「3-of-5」，他能評估的是名字。如果在 Dynamic Type 放大字級下名字排不進一行，代表門檻對櫃檯來說太大了：**n 要由手機螢幕決定，不是由密碼學品味決定**。

### C — 紙本錨定，機器比對

**D 的下游，不是平行軌。**

台灣已經在運作、編列預算、而且演練過一條全民離線出版管道，終點正好是 backupTW 的查驗者：2025 年國防部全民防衛動員署印製《當危機來臨時：臺灣全民安全指引》1,100 萬冊，2025-11-19 至 2026-01-05 送達 983 萬戶，經中華郵政分四批到 22 縣市鄉鎮市區公所，再走內政部民政系統（里長、鄰長），明白比照選舉公報模式。印製 4,279 萬元（每冊 3.8 元），投遞約 1,988 萬元（每戶 2 元），全案每戶約 5.8 元。法源上，行政程序法 §157(III) 已經讓政府公報**或**新聞紙的刊登成為生效要件；新聞紙那一支比公報那一支更重要，因為獨立的紀錄報產生一份國家事後改不掉的檔案——這正是 `TrustList` 自己的推理想要的東西。

三個必須改的地方：

1. **掃描只能確認，不能引入。** 這條寫進型別，不寫進註解：`matchedPrintedValue` 只能對機器已經持有的承諾值構造（`pinnedCommitment` 或鏈上已採用的那一版），用 private init 擋住所有其他路徑。否則我在收容所發燃料券的時候，順手發一張「信任清單核對卡（內政部民政司 印製）」，上面是我的承諾值，App 幫我蓋章。第一版把不可驗證的判斷從「比對摘要」搬到「這張紙是真的嗎」，判斷被搬家了，沒有被消除，而且搬到我唯一能量產的那個東西上。
2. **櫃檯用的不是家戶手冊，是護貝 A5 桌牌**，一個里辦公室一張，走民政管道。這個 App 今天所有的掃描都是螢幕對鏡頭、自帶光源（`QRTransport.swift` 為此寧可用 Q 級容錯多付四張 frame）；紙不發光。燭光下要一手拿手電筒、一手壓平受潮起皺的書頁、還要拿手機，後面排著隊。家戶手冊仍然有價值，但那是公民在自己家裡白天核對自己手機的場景，不是櫃檯儀式。
3. **鏈跑過一次真實輪替之前不要付印。** 983 萬份紙本收不回來。專案結束後，那些紙會比組織活得久，指向一份沒人維護的清單、一條沒人能推進的鏈——一份國家印製、國家投遞、背書一個已死的公民社會產物的小冊，正好是 §2 說對手想要的那種權威冒用面。

**櫃檯負擔：** 舉一張卡對著鏡頭，或輸入約 20 個字元。兩者都是 fail-closed。
**螢幕可以說：** 「與您掃描的紙本相符（2026-11-04 09:12）。」沒掃過時：什麼都不要說——一個從沒被執行過的儀式，不值得在每次結果畫面上佔一行永久文字。

## 四、建議

**A 與 D 的機制在同一個 release 出；C 在條件滿足前不印；B 是目的地不是備案。**

同一個 release 要含：一個釘死的承諾值、修好單射性的正規形式 v2（含 `nextKeys`、`killKeys`、`sequence`）、**能走的鏈走訪**、終止與分叉規則、以及一份 `nextKeys` 已經填上真值的 v1 清單。理由就是這個組織的觀測基準率：15 個月 39 個 commit、零個 tag、兩次超過五個月的靜默、三個 bonds-tw repo 同樣形狀。**在這種節奏下，排到「之後的 increment」的能力就是不存在的能力**；如果它進不了這一版，它也要從白皮書裡拿掉。

先出 A 的理由仍然成立——它是一天的工作，把這個 repo 最重要的一句未強制的註解變成編譯期常數，最壞情況就是今天的行為。但 A 單獨出貨是死路，它的輪替故事是加州公司加一條國際線路。D 用零組織成本買到輪替性質，而輪替是緊急狀態真正需要的、也是 bonds-tw 真的營運得起來的唯一一個。它在每個方向都安全降級：金鑰遺失、被攻破、鏈分叉、保管人失聯——裝置退回釘死的承諾值、拒絕第三方簽發者。那是今天的行為，是安全的。

**但在寫 §5 的第一行程式之前，有兩件事要先做完**，這是第一版排錯的順序：

1. **修單射性**（§5.0）。這是阻斷條件，不是待辦事項。
2. **量一次誠實路徑的成功率**：找真的里長、真的卡、晚上、有人排隊。第一版把涵蓋率當成 UI 語氣問題。如果那個數字很低，它的優先序高於整個 §5，而附錄那個問題——「緊急換發證者到底需不需要一份全國清單」——的答案大概是不需要，一個逐次相遇、在地見證的判斷可能更適合。這件事花一個下午就能知道，而 §5 的清單機制花的是幾個月。

**為什麼不先做 B**，這句要寫進白皮書：研究沒有找到**任何**由公民社會團體門檻持有公民身分信任根的先例。Tor 的 directory authorities 與 Sigstore 的 3-of-5 是最接近的部署案例，兩者面向開發者，依賴方是機器不是收容所裡的志工。做出世界第一個是以年為單位的治理工程。相對地，也沒有這種方案失敗的事後檢討——那是證據的缺口，不是安全的證據。

**為什麼 C 從平行改成下游**：第一版說 C 的前置時間由關係決定（全動署談內容、民政司與村里長談投遞），所以現在就開始談沒有成本。談是沒有成本，**印有**。付印的條件是：鏈已經由設計者以外的人執行過一次真實輪替，而且存在一個具名的人有權宣告專案結束。如果沒有這個人，誠實的做法是不要印。

## 五、先蓋什麼

門檻是**嚴格優於今天**：不接受任何今天會拒絕的東西，除非編譯期常數早就這麼說了；並在一個目前沉默的畫面上加一句為真的話。

### 5.0 阻斷條件：正規形式 v2（在任何承諾值被公開之前）

```
bonds.tw/trust-list/f1
seq	7
published	2026-08-09T00:00:00Z
entries	3
e	moica-g3	primary	內政部憑證管理中心	G3 錨，見 IssuerCertificate.swift
e	…
next	2	<H(pk_a)>	<H(pk_b)>	<H(pk_c)>
kill	<H(k1)>	<H(k2)>
end
```

- **拒絕分隔字元。** 所有進入正規形式的欄位一律拒絕 `\t`、`\n`、`\r`、全部 C0/C1 控制字元，以及雙向文字覆寫字元（U+202A–U+202E、U+2066–U+2069）。在 `validate()` 最前面做，早於一切。
- **`id` 限制成位元組定義的可列印 ASCII 子集**，並用 UTF-8 位元組序排序，不要用 Swift 的 `String.<`——後者是 Unicode 正規化感知的定序，跟 Python、Go 或「手抄」的結果不一定一致；更糟的是 `Set<String>` 認為 NFC 與 NFD 相等（重複檢查會攔）而序列化成不同位元組（摘要會不同），等值與序列化互相矛盾，正是第 30–37 行說正規形式要防的事。只要有人提議一個「比較好讀的中文 id」，正當的緊急輪替就會全機隊失敗，而且失敗的樣子跟被攻擊一模一樣。
- **承諾筆數與明確終止行**，每個欄位設長度上限。
- **性質測試：把 `canonicalForm` 反解回 entries，要求往返相等。** 這是安全性質，現有測試沒有一個測它。
- **跨實作測試向量**：commit 一份向量檔，要求一個非 Swift 的第二實作逐位元組重現。第 105–111 行的註解已經把跨實作一致宣稱為重點，目前沒有任何東西測試它。
- **`version` 拆成兩個欄位**：`formatVersion`（編譯期常數、有 guard、進域分隔字串）與 `sequence`（單調、對比裝置上的高水位）。現在這一個欄位同時扮演兩個角色：guard 拒絕非 `currentVersion` 的一切，而單調性規則要求它每次發佈都遞增——第一次真實輪替不是動不了，就是有人在戰時壓力下把 `unsupportedVersion` 的 guard 刪掉。`sequence` 相對目前持有值的跳躍要設上限，否則一份 `sequence: 2147483647` 的清單就永久關閉了序號空間。
- **單調性，並抄下它的理由。** TS 119 612 §5.3.15：較舊的清單「shall be discarded as expired as a measure to reduce the risk of a substitution by an attacker with an old TL」。永遠不接受小於或等於本機曾接受過的最大 `sequence`。這條不需要網路，而且跟到期不同，它不會在一支放了一年的手機上變成阻斷服務。

### 5.1 `backupTW/Presentation/TrustList.swift`

- `static let pinnedCommitment: String`（**一個**），來源區塊照 `IssuerCertificate.swift` 的寫法，寫清楚它在哪裡發佈過、那證明了什麼、不證明什麼。
- `nextKeys`（雜湊集合＋門檻）與 `killKeys` **v1 就存在、就進摘要、就會被走**。不要「解出來但拒收」——那會讓每一台已安裝的 v1 裝置拒收第一份帶著這個欄位的清單，於是輪替需要新的線路版本，而新的線路版本需要 App 更新，送給的正好是抽屜裡那支沒網路的手機。容許它是安全的，因為它在 `canonicalForm` 裡：攻擊者寫任何東西進去都會改變承諾值、對不上釘死的值。
- **先驗簽章、再解析。** 用預先承諾的雜湊比對隨附公鑰 → 驗 Ed25519 簽章（簽在收到的原始位元組上）→ 才進 `JSONDecoder`。解析前先做位元組層級的硬上限：總長度、entry 筆數、單欄長度、JSON 巢狀深度。CI 加上模糊測試語料。
- `validate(expectedCommitment:)` 回傳值而不是 `Void`。現在「沒有預期值不算通過」只靠註解執行，要讓它變成型別：

```swift
enum Provenance: Equatable {
    case pinnedInBinary(commitment: String)
    case walkedFromPinned(sequence: Int, commitment: String, adoptedAt: Date)
    case unconfirmed
}
```

  **只出兩到三個 case，不要預留 `matchedPrintedValue`。** 一個沒有產生路徑的 case，是在邀請未來的維護者去補一個產生路徑；C 落地時再加，那時每一個 switch 都會編譯失敗，那正是你想被強迫做的審查。

### 5.2 `backupTW/Presentation/OfflineVerifier.swift`

- `credentialIssuerIsNotTheSubject`（第 359 行宣告、第 857 行拋出）維持預設。只加一條接受路徑，只吃 `.pinnedInBinary` 與 `.walkedFromPinned`，其餘一律照舊拒絕。
- 新增 `issuerListIsUnconfirmed`，跟 `credentialIssuerIsNotTheSubject` 分開：原因不同、句子不同、下一步不同。
- **不要新增 `trustListRolledBack` 作為拒絕。** 對方手機上的清單版本，跟他的憑證能不能對這支手機已經持有的清單驗過，完全無關。較舊的來源清單靜默忽略、寫進 `SelfCheck`、櫃檯上看不到。**拒絕是給沒通過檢查的憑證用的，不是給信差的中繼資料用的**——在櫃檯上因為對方 App 比較舊而拒絕一個人，雙方都無計可施，唯一的解法是不要再用這個 App。
- 引擎的 `VerificationOutcome` 維持二元（`.verified` / `.rejected`），因為密碼學是二元的。三態在**畫面**上，由一個掛在 verified payload 上的 `IssuerStanding` 與 caveat 決定。這是我對審查者二的部分不同意：要三態的是螢幕，不是引擎。
- `OfflineVerifierTests` 的無網路 canary 目前只解析一條寫死的路徑（`backupTW/Presentation/OfflineVerifier.swift`）。改成**列舉整個原始碼目錄**，讓新檔案預設被涵蓋、而「目錄裡有但沒被列舉到的檔案」才是讓測試紅掉的條件。逐檔手動維護的步驟，在作者停止關注後加入的第一個檔案上就會被跳過，而且跳過是看不見的：測試照樣綠，只是涵蓋得比較少。這條防的是這個專案名字裡那個性質。
- 再加一個同族的：**no-crash 語料測試**。在櫃檯上當掉的驗證器，跟會說謊的驗證器一樣完全地失敗任務。

### 5.3 `backupTW/Presentation/TrustListStore.swift`（新檔）

已採用清單的儲存，含單調高水位，`.completeUnlessOpen` 比照 `CredentialStore`，持久化 `(formatVersion, sequence, commitment, acceptedAt, provenance)`，讓回滾嘗試在重開 App 後仍然可診斷。**高水位放 Keychain**，讓它撐過重灌；換機或還原到新裝置時它會歸零，那是已知的洞，寫進 §8，不要用「單調性嚴格優於到期」的說法蓋過去。

另外存**掃描歷史**（掃過的值與日期），不只是高水位。因為承諾值不符會是常態：C 的節奏是幾年一版、A 的釘子隨 release 動、D 隨時可輪替，所以紙本比手機舊、或抽屜裡的手機比紙本舊，都是日常。第一版寫了「相符」的文案、寫了「尚未核對」的文案，**從頭到尾沒寫「不符」的文案**，而那是基準案。要拆成兩種結果、兩種文案、兩種視覺重量：

- 「您掃描的紙本比這支手機上的清單舊」——預期內、良性、講一句然後繼續。
- 「這支手機上的清單，和您掃描過的任何一張紙都對不上」——停。

**良性那句先寫**，它會被讀一萬次。一個大多數時候在良性狀況下響的警報，就是用 70.2% 的忽視率去買它唯一一次為真的機會。

### 5.4 相遇時交換版本號（freeze 偵測）

扣留沒辦法讓它失敗，但可以讓它大聲。每次相遇交換一個東西：**我見過的最大 `sequence`**（只有數字，不是清單）。持有 v3 的裝置遇到聲稱 v4 的對方，就記下「存在一份我拿不到的較新清單」，並持續顯示。這是不需要網路、不需要時鐘、不需要到期的凍結偵測器，而且是我扣留清單時無法同時壓制的訊號——除非我連相遇一起壓制。

三個約束：**（一）** 這個數字絕不能塞進出示用的 QR carousel。`QRTransport.swift` 每張 frame 364 payload bytes，`PresentCredentialViewController.swift` 的 `frameInterval` 是 0.55 秒，第 543 行自己記著「A holder who expects two seconds moves the phone away at four and restarts the scan」，卡片簽章的出示已經是十四到十五張、一輪接近八秒。信任清單本身**永遠不進出示 payload**，要傳就走另外發起的檔案／AirDrop／BLE 傳輸，離開查驗者正在計時的挑戰－回應流程。版本號只在 BLE session 與最後一張 frame 的剩餘容量裡搭便車，塞不下就丟掉。**用 `PresentationFrameCountTests` 斷言：任何信任清單狀態都不得增加出示的 frame 數。** **（二）** 這個數字未經驗證，所以可以被灌假的「有更新」，那是顯示層的騷擾而不是信任提升；接受它，因為它唯一導致的動作是「去拿一份更新」，那無害。**（三）** 它永遠不 gate 驗證。

### 5.5 `backupTW/Diagnostics/SelfCheck.swift`

三列 `.informational`：這支手機持有哪一份清單（`sequence`、發佈日、承諾值前 8 碼、provenance）；**這條鏈上一次出現生命跡象是什麼時候**（任何一份有效簽署的後繼版本，包括除了序號與日期以外完全相同的 no-op 版本）；以及被忽略的較舊來源清單。

「上一次生命跡象」這一列是為了補上 §6 拒絕到期之後留下的缺口：**一條從來不需要輪替的鏈，跟一條再也無法輪替的鏈，在每一台裝置上位元組完全相同**。它同時給保管人一個定期動用金鑰的理由——對於「三年沒碰過的金鑰，位置、密語、編碼都不見了」這件事，那是唯一已知的防禦。

### 5.6 畫面

**四種收尾，只有一種是紅的：**

- **✓ 綠**：MOICA 路徑，簽章與挑戰都過。
- **◐ 橘（「只有一半」）**：簽章過了，但簽發者的地位來自這支手機上的一份清單。**第三方簽發者必須改變判定 token，不能只是多一條 caveat。** `VerificationCaveat.Group.aboutTheDocument` 已經可以放到七條，而 `OfflineVerifier.swift` 第 212 行的契約是「nothing here may collapse or reorder within a group」，所以一句放在第五條的話，在櫃檯上等於沒有。`CapabilityViewController.swift` 已經把這套詞彙建好而且辯護過了（`.partial(actually:)`、`◐`、`.systemOrange`、第 168 行「A tick would be the lie」），照抄。燭光下一個字符勝過一個句子。
- **灰（中性）**：無法驗證——沒有東西可驗、對方沒有憑證、快照缺席。**不是紅的。** 按 §2 的數字這是多數情況，而被查的人看不到螢幕，只聽得到語氣。
- **✕ 紅**：簽章不符、挑戰不符。留給真的是這份文件有問題的情況。

其餘規則：
- **驗證畫面上不出現任何承諾值**，8 碼也不要。它去 `SelfCheck`。
- 陳舊度是**在裝置上算出來、每天都會變的數字**：「發佈於 2026-08-09（距今 187 天）」。「自安裝以來沒有更新過」是一句在第一天是資訊、第六個月是壁紙的常數文字，而且因為 §8 的扣留問題，它會永久為真。時間長度會被讀，日期不會。
- 清單來的每一個字串都走 `UntrustedText`，包括 `publishedAt` 與版本句。`publishedAt` 用嚴格 ISO-8601 解析，不合就拒——它在摘要裡，所以格式錯是發佈者的 bug，不是相容性問題。**「（不是內政部）」這個括號絕不要跟攻擊者可控的文字排在同一行**，雙向覆寫字元搆得到。
- **任何地方都沒有「標記為已信任」的開關。**
- Home 在查驗開始**之前**就顯示清單的年齡，不是查驗之後的 caveat。`CircuitAssets.swift` 已經記著這個專案的承平時期準備義務長期沒被履行（27.7 MB 撤銷快照要 24 小時重抓，81.5 MB 下載、約 950 MB 磁碟，而且它自己的檔頭說「備妥」的意思是「那 82 MB 已經下載好了，你不用在櫃檯前等」，不是「沒訊號也能用」）。
- **`credentialIssuerIsNotTheSubject` 與 `issuerListIsUnconfirmed` 的畫面上要寫下一步是什麼。** 沒有下一步的拒絕不是拒絕，是把人推去用「我認識這個人」。

### 5.7 不是程式碼，但排在程式碼前面

- **櫃檯桌卡**（A5，一里辦公室一張）：App 說 X 的時候做 Y、找誰。任何一條找不到 Y 的拒絕，就不該以拒絕的形式出貨——併成通過上的 caveat。
- **輪替 runbook 加驗證腳本進 repo**，並在程式落地的同一週做一次 v1→v2 的演習，由**設計者以外的人**照文件獨力執行。「離線產生、用一次、銷毀」是三個動詞，不是操作手冊；六個月後執行的人手上只有一個叫 `nextKeys` 的欄位，不知道用哪條曲線、哪種編碼、到底簽哪些位元組。用錯編碼簽出來的 v2 是一份沒有裝置會接受的 v2，而前一版已經承諾了那些雜湊。門檻式的後繼集合同時就是這裡的復原路徑。**沒有演練過的儀式等於不存在的儀式。**
- **bonds.tw 一次付到最長年限**，趁還有錢。`canonicalForm` 第 113 行把 `bonds.tw/trust-list/v…` 寫死當域分隔標籤，域名易主不影響那個標籤——但每一份說「去 bonds.tw 查承諾值」的人類指示都會失效，任何人重新註冊就能在你自己文件指名的來源真實網址上，端出一份看起來很合理的清單和相符的承諾值。這是整份文件裡成本最低的完整攻陷，第一版一次都沒提到。三件事：付到最長年限；在 `TrustList.swift` 註明這個字串是永久的域分隔標籤、即使域名易主也絕不能被改成抓取端點；**永遠不要把「去 bonds.tw 查」當成取得承諾值的指示**——直接印出承諾值本身，並指名至少一個不是域名的場所（鏡像 repo 的 git object hash、紙本）。
- **能力金絲雀測試**：照 `OfflineVerifierTests` 既有的手法（`theVerifierSourceNamesNoNetworkingAPI` 用測試斷言一件否則只能用散文宣稱的性質），加一個在「畫面上顯示了某個能力字串、但沒有任何程式碼路徑會產生它」時失敗的測試。這不是假設性的問題：bonds.tw 曾經出貨過一個邀請大家簽署一面不存在的連儂牆的區塊，每個 CTA 都是 `href="#"`，而修好它的那個 commit 在 `bond-website/src/components/sections/SectionWall.tsx` 第 73 行自己寫著，那是「the same defect the app this site is for spends its whole codebase refusing」。**在 v1 出貨之前，把白皮書修剪到 v1 真的做得到的範圍**，不是出貨之後。

## 六、絕不要蓋什麼

1. **抓取。** 驗證時、啟動時、藏在「僅限 Wi-Fi」開關後面都不行。開 socket 的驗證器等於交出一份「誰在哪裡、什麼時候被查」的紀錄，那是 §5.2 拒絕的監控，而且它在訊號完全正常時照樣成立。白皮書要具名 **ToIP TRQP v2.0** 作為沒走的那條路：它的回應是未簽名的即時查詢結果，沒有快取語意、沒有回應簽章、沒有新鮮度處理、沒有完整性保護，所以原理上就不能被儲存後重用——而 VC 生態系有一大塊正往那裡去。
2. **`TrustList` 上的單一簽章者 `signature` 欄位。** 第 41–47 行的推理是對的。簽章要來，只能以**前一版事先指名**的形式來（D／B），它回答的是「你已經信任的那份清單指名的人簽的」，不是「某個權威簽的」；永遠不要變成 struct 上的 `let signature: Data`。
3. **到期或 `nextUpdate` 欄位。** 現行的 AAMVA VICAL 把 `nextUpdate` 設在 `date` 之後 24 小時——backupTW 的驗證器隔天早上就握著一份過期的信任清單，而且在這個 App 存在的理由那個情境裡是永久過期。TUF 繼承下來的規則更糟：「if the trusted root metadata file has expired, abort the update cycle」，Sigstore 的根大約一年到期。比到期長的封鎖，會在鏡像路徑最需要的時候把它關掉。**改用單調序號**——對「用舊清單替換」是同一個防禦，而且在一支黑了一年的手機上不用付代價。代價是沒有壽命訊號，用 §5.5 那一列補，不要用到期補。（VICAL 的 `certificateInfos` 欄位形狀——`certificate`、`serialNumber`、`ski`、`docType`、`issuingAuthority`、`issuingCountry`、`notBefore`、`notAfter`——值得拿來對照現在這個過瘦的 `{id, displayName, note, isMirror}`；它的信任啟動不值得抄，因為 AAMVA DTS Root CA 是從 AAMVA 自己的主機用 TLS 下載的自簽憑證，指紋沒有在任何別的地方發佈過，抄它等於再進口一份 `IssuerCertificate.swift` 的 TODO。）
4. **RFC 5011 式的 in-band 採用。** 它看起來像標準答案，而且結構上就是線上專用：§2.3 要求至少每 15 天輪詢一次，§2.4.1 要求 30 天的 add hold-down 期間內出現兩次通過驗證的觀察。整段期間離線的裝置永遠累積不到觀察、永遠不會採用金鑰。把整份 RFC 拿去 grep offline / disconnect / stale / not running，**零筆**——它不是在離線案例上失敗，它從來沒想過離線。何況 2018 年那次根 KSK 輪替，有十年準備、延後一年、網路正常，幾個月後仍有超過 9,000 台解析器卡在 KSK-2010。輪替要照 TUF 的鏈走訪或預先指名，不要照 hold-down。
5. **關鍵路徑上任何由人做的摘要比對，尤其是「這三個裡哪一個對？」** 那是所有量測過的配置裡最差的：**72% 沒發現攻擊**，顯著差於比對十六進位，而且受測者對誤報**更不擔心**。圖片也不行：頭像式指紋漏掉 54%，OpenSSH 自己的原始碼用最強烈的措辭否認 randomart 的安全價值。
6. **「標記為已信任」的開關，或任何讓查驗者推翻拒絕的介面。** SOUPS 2018 量的就是這件事：20 人中 12 人沒比對就撥了開關、18 人相信自己安全地完成了。EUDI ARF 的離線條款是同一個錯誤的制度版：Relying Party Instance 在離線又沒有快取狀態清單時，「performs a risk analysis considering all relevant factors for the use case, before taking a decision to accept or refuse」——那是一句站在演算法位置上的政策文字，把決定下放給收容所櫃檯上一位沒有受過訓練的志工不是備援。
7. **只能加、不能減的 `isMirror`。** `Entry` 的狀態必須表達得出 superseded／distrusted，而且因為 `canonicalForm` 已經涵蓋所有欄位，承諾值免費涵蓋它。改 entry 的狀態，不要改摘要的定義。
8. **輪替故事是「發一版 App」的任何東西。** 對 iOS App 來說，binary 的真正信任根是 Apple 的程式碼簽章加 App Store 可達性，兩者都不是台灣的、封鎖時也都不在。A 之所以被允許有這個性質，只因為它被明確標示為地板，而且螢幕上這樣說。（另外要單獨決定：緊急時到底有沒有分發路徑——sideload、TestFlight、Android build、清單的紙本 QR——這是同一個問題往下一層，目前仍然無解。）
9. **OpenTimestamps 或任何鏈上錨定作為驗證時機制。** 它自己的文件寫著「to verify timestamps you need a local Bitcoin Core node」。那是取消資格，不是可調參數。只帶區塊頭的變體需要持續有人快遞區塊頭、在 iPhone 上做工作量驗證，而且買到的仍然只是「這個承諾值在時間 T 之前就存在」，永遠不是「這個簽發者是正當的」。時間戳回答的是順序；收容所門口那個里長問的是權威。**`TrustList.swift` 第 26 行的「an on-chain root」請刪掉**，預先指名的鏈用千分之一的複雜度給了同一個回滾保證。
10. **等 TW DIW。** MODA 自己在 W3C TPAC 2025 的材料把可信簽發者清單描述成一個由 MODA 維護、部署在 **Arbitrum Sepolia 測試網**上的 API，撤銷列為未解。API 正是 backupTW 存在來繞過的那個單點，測試網不是耐久的發佈媒介。不要設計交接，也不要讓「TW DIW 憑證可離線驗證」的行銷說法，跟「驗證方能離線決定哪些簽發者算數」混為一談——這是兩個主張，只有前者為真。
11. **把愛沙尼亞 ROCA 復原或烏克蘭 Diia 當成離線先例。** 兩者都會被審查者提出來，所以要先擋。愛沙尼亞的補救（49.4 萬張中 35.4 萬張遠端更新）之所以可行，是因為一個友善、主權完整、承平的國家有一張能用的網路可以把卡重新換鑰，RIA 自己的報告就把這點列為愛沙尼亞與別人不同之處；即使如此，從通知到停用花了 65 天，到撤銷花了七個月。Diia 的驗證碼是一次性、三分鐘有效、不帶個資的查詢 token，不是憑證，而且連 Diia 自己標成「離線」的流程，結尾都是查驗公司的資訊系統收到一份 PDF——那裡的「離線」是指公民人在現場。烏克蘭真正的戰時策略是**保住通往中央簽發者的網路路徑**（依 2075-IX 法與內閣第 1500 號決議把 161 個登記系統、約 15 PB 搬上雲，3 萬多台 Starlink）。那是跟 backupTW 相反的賭注，也是 MODA 的賭注（700 台境內 NGSO 終端、70 個 backhaul 站點、3 個海外站）。引用它們時要說這是 backupTW 要取代的東西，不是要模仿的模型。
12. **（新增）把信任清單塞進出示用的 QR carousel。** 見 §5.4。它是定義上的 out-of-band 產物；讓它增加 frame 數，等於讓一個絕大多數用不到這個功能的人去付成本，那叫回歸。
13. **（新增）驗證畫面上出現任何承諾值。** 見 §1.3。
14. **（新增）因為對方的清單比較舊而拒絕。** 見 §5.2。
15. **（新增）n=1 的接續金鑰，或全部保管人都在 ROC 管轄內的門檻。** 見 §1.4 與 D。
16. **（新增）鏈跑過一次真實輪替之前付印。** 見 C。
17. **（新增）只有型別、沒有產生路徑的 `Provenance` case。** 見 §5.1。

## 七、還要有人去查清楚的事

**GRCA 的金鑰啟用見證書到底有沒有發佈過？** CPS §6.1.4(4) 規定透過媒體公告，§6.1.1.1 描述一個經稽核、全程錄影、產出記載公鑰的簽署見證書的儀式。第一代、1.5 代、第三代都找不到已發佈的見證書——沒有公報引用、沒有紀錄報、沒有可取回的產物。如果它存在，它就是讓整套承諾設計在台灣語境下站得住的引用。**如果不存在，那個缺席本身就是值得發表的治理發現**，也是「為什麼一個公民社會專案不得不自己蓋一套」最強的論據。這件事值得寫一封信問數位發展部／GRCA，而不是兩邊都用猜的。同一封信要問：MOICA 或 GRCA 到底有沒有在任何 out-of-band 管道發佈過根憑證指紋？`moica.nat.gov.tw` 與 `grca.nat.gov.tw` 上都找不到，若真的沒有，`IssuerCertificate.swift` 那個 TODO 目前**原理上就沒有答案**。

**時鐘。** 所有系統的新鮮度與轉換規則都假設時鐘大致正確，`IssuerCertificate.swift` 已經為此帶著 `trustAnchorNotYetValid`。要明確決定：一台認為現在是 1970 年的裝置，拿到信任清單要怎麼辦。單調序號加拒絕回滾在完全不信任時鐘的前提下就拿到大部分好處——這是偏好單調性勝過到期的第二個獨立理由。

**緊急換發證者到底需不需要一份全國清單？** 所有被調查過的系統回答的都是「對於名稱 X，哪一把金鑰有權威」。收容所裡查驗鄰居的里長，可能在回答另一個問題——「這是不是我們鄉鎮被告知的那個鏡像簽發者」——而那個問題也許用逐次相遇、在地見證的判斷更適合，不需要全國清單機制。**這個問題要在 §5 的清單機制開工之前回答，不是列為後續研究。** §1.3 引的每一個錯誤率都來自年輕、受過教育、被提示過、而且把比對當成主要任務的受測者，那幾篇研究的作者自己說真實使用者會更差；凌晨三點拿手電筒的 70 歲里長不在任何一個已發表的樣本裡。目前對里長的數位素養、裝置持有、以及壓力下願不願意執行任何儀式，**沒有任何田野資料**。

## 八、這個設計仍然沒有解決的事

**扣留。** 我不需要偽造任何東西，只要讓正當的更新永遠不抵達。誠實那邊每一次更新的種子（bonds.tw、GitHub release、App Store）都只能穿過我；之後的散佈是相遇時的點對點，而相遇發生在我控制的地方——收容所、檢查哨、救濟隊伍、加油排隊。人肉網路在這裡不是對稱的，鞋子是我的。§5.4 的版本號 gossip 讓凍結變得看得見，不會讓它失敗；而 gossip 本身未經驗證，可以被灌假的「有更新」。**這個系統照樣做的事：** 繼續用它手上那份清單工作，永遠不到期，並且每天把「發佈於 X，距今 N 天」這個數字算給人看。如果我扣留的正好是那份要把某個被我接管的簽發者降級的清單——也就是 §2 認定比較重要的那一半——那個降級就不會發生，而且事後沒有痕跡。

**達到門檻的脅迫。** 2-of-3、跨兩個管轄區，擋得住一次拘留，擋不住兩次。真的擋不住的時候，鏈就是對手的，而且螢幕上那句「每一版都由前一版事先指名的金鑰簽的」會是**真的**、令人安心的，並且描述著一份偽造品——那是這個 App 裡最好用的洗白句子。終止金鑰是唯一的退路，而終止金鑰的持有人也可能被脅迫。**這個系統照樣做的事：** 讓終止是 1-of-N 而且便宜，讓被觀察到的分叉等同終止，讓最壞情況是退回今天的行為。代價要說清楚：任何拿到一把終止金鑰的人，可以永久關掉整個機隊的鏡像功能。我們接受這個阻斷服務，因為它的方向只有減。

**對手另立驗證器。** 我可以完全不理會 backupTW：發我自己的驗證器、我自己的證件，並讓出示它成為拿到燃料、暖氣、撤離名額的條件。密碼學在這裡買不到任何東西。**白皮書要直接寫：backupTW 阻止不了一個強制性的敵對證件體制，它從來就不打算阻止。** 它能做的是讓一個公民不必問國家，就能向**另一個公民**證明一件事。把這句話講出來會重排整個計畫的優先順序：鄰里之間的可信度、以及誠實路徑的涵蓋率，都排在全國鏡像簽發者清單前面。這也是第一版沒做的比較——它把 A、B、C、D 互相比，從來沒有把它們跟「根本不做這個功能」比。

**涵蓋率。** 天花板大約是人口的 15–18%。加上沒電的手機、破掉的螢幕、從來沒裝過的人、以及晚上 300 人隊伍裡一輪 8 秒的 QR carousel，櫃檯上最常見的結果就是「無法驗證」。我不需要製造這件事，我只要不去修它。一個星期之內，里長的運作規則會變成「這個 App 都不會動，用戶籍、用判斷」，之後我的偽造證件不需要通過驗證，它只需要被一個穿制服的人自信地拿出來。**這個系統照樣做的事：** 把「無法驗證」做成中性的灰、不是紅的，並在那個畫面上寫出下一步。但這件事不是密碼學問題，也不是 UI 語氣問題，它是這個計畫的主導風險。

**重灌與換機把單調高水位歸零。** 高水位放 Keychain 可以撐過同一台裝置上的重灌；換到新裝置或從備份還原，它會從釘死的承諾值重新開始，也就是重新回到一個能接受任何一份正確簽署的後繼清單的狀態，包括我在那之前造好的那一份。這是到期機制沒有的洞，第一版主張單調性嚴格優於到期時沒有提。目前沒有修法，只有登記在案。

**分叉不裁決。** 兩條都正確簽署、從不同起點走過來的鏈同時出現時，密碼學無法告訴里長哪一條是真的。這個系統的做法是不裁決——熄燈，退回內建錨。這是刻意放棄的能力，代價是拿到門檻金鑰的人可以用一次分叉關掉功能。

**組織死掉之後。** 觀測到的基準率是 15 個月 39 個 commit、零個 tag、兩次五到七個月的靜默。專案結束後，白皮書、bonds.tw 上的文字、以及（如果印了）紙本，都會活得比組織久，而裝置上的 App 分不出「還沒發生緊急狀態」和「這個機制 2027 年就死了」。§5.5 的「上一次生命跡象」那一列讓衰亡變得看得見，能力金絲雀測試讓兌現不了的宣稱編譯不過去，C 在條件滿足前不印——但沒有任何機制能在事後把一個沒人維護的信任錨收回來。**如果沒有一個具名的人有權宣告專案結束，那份紙就不該印。**

**`IssuerCertificate.swift` 的 TODO 仍然沒有答案。** 整條鏈的第一個錨——MOICA G3 的指紋——是從 `*.nat.gov.tw` 透過 TLS 拿到的，沒有跟任何 out-of-band 的東西核對過，而 §7 的查證顯示可能根本沒有可核對的東西存在。這一版把上面每一層都做得更硬，但沒有動到那一層。

**沒有任何里長的田野資料。** 這份文件裡每一個關於「查驗者做得到什麼」的判斷，都是從別人的受測者外推來的，而那些受測者年輕、受過教育、被提示過、把比對當成主要任務。這份設計對它自己的使用者，一個實測數字都沒有。
