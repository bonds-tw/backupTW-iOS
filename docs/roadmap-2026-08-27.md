# 有備而來(Bonds)開發 Roadmap — 2026-08-27

由 `bonds-roadmap` workflow(6 平行評估 + 彙整)產出。基準:當日 OID4VCI 領卡 + OID4VP 出示對官方 demo 端到端打通。

> **2026-08-31 現況更新（優先於本文較舊的「缺口」敘述）**
>
> - 首頁已分成國民身分證／政府卡片／MyData 三個來源，TWDIW 卡詳情、欄位中文對照、Face ID／手機密碼入口、App 自己的 did:key、每證件獨立 key，以及 API＋Arbitrum 信任紀錄畫面均已落地。
> - MyData 已有八個實際 `personal/detail/API.*` 項目、受保護且不備份的原始檔 archive、首頁 inventory、專用詳情、取得時間／格式／SHA-256 指紋重驗、PDF/ZIP 內 PDF 預覽、重新取件與單項刪除。原始檔是保險箱的唯一事實來源，不再為了顯示而製造 self-issued credential。
> - MyData 下一個完成門檻不是再補模型，而是用真實帳號逐項驗證八個資料項目的下載格式、可預覽性、更新與刪除，並讀取 `PDFSignatureScan` 的實測結論。
> - 信任中心目前「顯示」API 與鏈上是否一致，但收卡授權仍只使用 API 清單；把鏈上查核結果接進收卡門檻，是下一個安全性 P0。
> - Release 簽章／ZKP 仍受 bonds-tw 後端缺席所阻；本文後段關於這個限制仍有效。

## Executive summary

有備而來已經在 8/27 把 OID4VCI 領卡與 OID4VP 出示(含選擇性揭露)對官方 demo 端到端打通,工程紀律也好(92 個測試檔、僅 1 個 TODO、閘門實機擋住前綴攻擊)。但兩個結構性事實決定了現在該做什麼:①目前所有「完成」幾乎都是 DEBUG build 的完成,Release 版的簽章/驗證金鑰全被 #if DEBUG 關掉,根因是 bonds 後端還不存在——它同時卡住 Release 上架、ZKP、連儂牆、Matters helper、nullifier 去重五件事;②北極星「電信卡→超商取貨」的領卡 pipeline 其實與卡別無關、已就緒,真正缺口不在 App 端,而是「從沒觀測過任何一張真實電信 offer 的結構」,使用者以為的入口 twm5g.com 實測是台灣大客服 App 死路。因此最該先做的單一動作是:用真門號跑一次官方領電信卡流程、用 mitmproxy 抓下 offer 結構與欄位型別——這是唯一的關鍵路徑阻塞,下游的閘門、選擇性揭露、超商卡顯示全部等它。在等這個實測的同時,UIUX 與卡片顯示有幾個不依賴任何外部相依、成本低價值高的快贏(TWDIW 卡詳情頁、名詞/動詞分區、ZKP 能力頁誠實化)可以並行推進。

## 建議執行順序

1. 用真門號跑官方領電信卡流程 + mitmproxy 抓真實 offer 結構(唯一關鍵路徑阻塞,一次解鎖北極星、超商卡欄位型別、選擇性揭露決策)
2. 確認台灣大/中華電信 issuer host 在 43 筆信任清單(S,可與第 1 步並行,純量測低風險)
3. 首頁名詞/動詞分區 + 卡片依三來源分區(UIUX 快贏,不依賴任何外部相依)
4. 新增 TWDIW 卡詳情頁,移除 open() 的 alert 死路(讓收得到的卡真的看得到內容)
5. 誠實化 ZKP 能力頁主張(S,高價值,拆掉 demo 現場被誤讀成『本人此刻已驗證』的地雷)
6. 處理非字串揭露的寬鬆顯示(依賴第 1 步的真卡型別,是超商取貨情境的必要條件)
7. 定案 MyData PDF 是否帶官方簽章 + 立保險箱 IA 骨架與空狀態(讓目標 3 在首頁對等呈現)
8. 逐條送出上游回報(使用者拍板身分與條數後執行,不可逆對外動作)
9. CI 補 UI 測試與覆蓋率門檻 + 關掉 IdentityReset 半殘狀態(工程健康與隱私正確性)
10. 決定並開始 bonds 後端 v0(此後才解鎖:ZK Release 端到端、連儂牆上線、Matters helper、nullifier 去重、撤銷根鏈上錨定這批 XL 項)

## 主軸(tracks)

### 收真實證件/電信卡→超商取貨(北極星)

**為什麼**:領卡 pipeline 與卡別無關且可重用(OID4VCICollection.collect 依 configuration id 存 serialized credential,不 hardcode 駕照欄位),in-app 掃碼領卡已完整接線並能解官方格式,真實中華電信 issuer host chtmecard.wallet.gov.tw 也在 43 筆信任清單內。缺口全在 App 之外:電信/超商卡要走電信商真實門號驗證才發卡,那一步不在 backupTW 內,且至今沒觀測過任何一張真實電信 offer 的結構。使用者給的 twm5g.com 實測是台灣大客服 App(twmcsapp://)死路,不含 VC。

**第一步**:拿一張真實中華電信門號,在官方皮夾 App 走一次領電信卡,mitmproxy 觀察門號驗證後 issuer 發的 credential-offer-object 長相、issuer host 是否 chtmecard.wallet.gov.tw、以及電信卡 phone / 超商卡 Phone_number_last3 的欄位型別。沒有這份實測,所有下游都是對 demo 駕照卡的臆測。

**里程碑**:
- (L) 用真門號跑官方領電信卡流程 + mitmproxy 抓 offer 結構(issuer host、grant 型別、credentialSubject 欄位型別)——這是唯一關鍵路徑阻塞
- (S) 確認台灣大/中華電信 issuer host 在 production 43 筆信任清單(curl frontend.wallet.gov.tw/api/did 逐頁抓到空,避開 size=20 分頁陷阱)
- (M) 處理 Phone_number_last3 等非字串揭露(超商卡出示到櫃檯不被判壞卡) — 依賴:用真門號跑官方領電信卡流程 + mitmproxy 抓 offer 結構
- (L) (僅在實測確認電信商採 app-to-app 喚起皮夾時才做)建 universal link 收 offer 入口或爭取對方發 openid-credential-offer:// — 依賴:用真門號跑官方領電信卡流程 + mitmproxy 抓 offer 結構

### 卡片顯示(收到 TWDIW 卡之後的內容呈現)

**為什麼**:收到的 TWDIW 卡目前完全沒有內容畫面:HomeViewController.open() 只對 selfIssued+usable 推詳情頁,其餘一律跳 alert『此版本無法開啟此卡』,disclosedClaims 已在記憶體卻無處顯示——這是列得出、打不開、出示不了的死列。且 SelectiveDisclosure 對非三元素/非全字串揭露會拒整張卡,把真實電信/超商卡直接判成 unreadable。這條與北極星直接綁在一起:收得到卡卻看不到內容等於沒收到。

**第一步**:做一個和 StoredCredentialViewController 平行的 GovernmentCardViewController,顯示卡種、發卡者 DID、效期、撤銷狀態(誠實標『需連線、無離線信任錨』)與 disclosedClaims 的 reveal/hide,並把 HomeViewController.open() 對 twdiw 卡改推此頁。

**里程碑**:
- (M) 新增 TWDIW 卡詳情 ViewController(仿 StoredCredentialViewController 讀 TWDIWCredentialReader.read),移除 open() 的 alert 死路
- (L) 『非標準揭露』寬鬆顯示:非字串/非三元素欄位不再拒整張卡而是標『此版本無法顯示』,但絕不弱化 undisclosedDigest 承諾驗證(偽造揭露仍須拒) — 依賴:用真門號跑官方領電信卡流程 + mitmproxy 抓 offer 結構
- (S) TWDIW 欄位中文標籤對照(駕照/電信/夥伴卡 claim key,以官方 moda-gov-tw/TWDIW-official-app 命名為準,不自己猜)

### MyData 資料保險箱

**2026-08-31 現況**:保險箱本體已落地。國民身分證仍採「讀取後 purge、只留下證件」的高敏感資料策略；其他 MyData 文件則在使用者選擇匯入後，把原始檔保存在 `MyDataVaultArchive`（Application Support、Data Protection、excludedFromBackup），以項目 id 建索引並記錄 SHA-256。首頁直接從 archive 列出文件，詳情可重驗指紋、預覽 PDF／ZIP 內 PDF、重新取件與單項刪除。八個 MyData 路徑已各自配置，學歷因不屬於 MyData 項目而明確排除。

**下一步**:用真實 MyData 帳號逐項驗證八種文件：下載格式、原始檔能否重新開啟、更新是否替換同一 id、刪除是否同時移除 original/meta、重新啟動 App 後是否仍可見；同時讓 `PDFSignatureScan.record` 落地，確認文件級簽章狀態。這一關沒有真實資料，不能用單元測試代替。

**里程碑**:
- (S) 定案 MyData PDF 是否帶內政部官方簽章(跑一次真取件讓 PDFSignatureScan.record 落地,讀 Diagnostics 的簽章列)——決定保存『原始簽章 PDF』還是『自簽 VC』,是所有後續設計前提
- (完成) MyData 文件 registry 與八個 item path；學歷排除並記錄原因
- (完成) 受保護的原始檔 archive、取得時間、格式、SHA-256 metadata、舊 metadata 相容與單筆／全部刪除
- (完成) 首頁資料清單、空狀態、專用詳情、指紋查核、PDF 預覽、重新取件與刪除；保險箱不再借用 CredentialStore／身分證詳情
- (M) 真實帳號逐項驗證八種文件並把結果寫成 fixture／相容性表
- (M) 若真實文件不是 PDF／單一 PDF ZIP，按實測格式新增安全的內嵌檢視器，不憑猜測解析

### ZKP 收尾

**為什麼**:軟體骨架出乎意料完整且誠實(prover 自檢會擋掉不滿足約束仍『成功』的陷阱、七條 caveat 但書機制、缺必要 caveat 的 package 會被拒),8/18 UX 稽核點名的 ZK 缺陷多已修。但今天『不可展示』有兩個硬阻:①Release 版簽不了也驗不了(isSigningAvailable/makeSigner 在 release 回 false/nil,因 bonds 後端不存在);②協定層 signatureMaterialIsReplayable——TW FidO SIGN 不簽 challenge,(cert, signed_response) 成永久 bearer token,『這個人此刻證明自己』根本不成立。

**第一步**:改 CapabilityViewController/PresentationScenario/CardCapability 的主張與 caveat 顯示,把能力頁那唯一與第一條但書自相矛盾的綠勾誠實化——S 級、低風險、立即降低 demo 誤讀風險。

**里程碑**:
- (S) 誠實化能力頁主張(把 wasTaiwanese 從 .supported 改 .partial,主張從『你持有』改成『某位持卡人的簽章材料被用了』)——不能靠但書補,要改主張本身,現場 demo 才不會被讀成『本人此刻已驗證』
- (L) 接上公開訊號 FFI 匯出(讓本機讀得到 nullifier/appID/smtRoot/challenge),ZKPublicInputs.parse 已寫好只等資料;做到後才能驗 challenge 綁定、比對 smtRoot、去重 nullifier — 依賴:上游(openac-mobile/mopro.swift)新增 zk_last_signals 對等匯出
- (XL) 讓 ZK 在出貨版本可端到端跑(簽章繞經後端、verifying key 可安裝) — 依賴:決定 bonds 後端 v0 範圍與是否做

## 風險與未知

- 電信卡/超商卡的真實 offer 從未被觀測:任何『pipeline 直接吃得下』的結論都建立在 demo 駕照卡的類推上,真卡可能帶非字串揭露或非 pre-authorized_code 的 authorization_code grant 而翻車(後者需實作另一條協定腿)
- 第三方數位皮夾能否取得官方介接資格是最大不確定性:電信卡的門號驗證發生在電信商/官方皮夾 App、MyData 官方 API 需『資料需求方』註冊契約——若不能取得資格,MyData 註定只能停在 WKWebView scrape、電信卡可能只能靠手動掃碼
- ZKP 安全主張站不住:signatureMaterialIsReplayable 讓 (cert, signed_response) 成為永久 bearer token,任何拿過一次回應的人(含內政部、SP operator)可永久鑄證,『本人、此刻』不被支撐;真正的修法是內政部讓 SIGN 簽查驗方選定的 challenge,屬協定改動、非本 repo 能做
- Release 全鏈簽章關閉是隱形天花板:沒有 bonds 後端就永遠上不了 TestFlight/App Store,demo 也只能靠 DEBUG-only sandboxDemo 路徑——別把 DEBUG build 的完成當成產品完成
- modadigitalwallet:// 刻意不註冊是對的安全決定,但代表若電信商只發這個 scheme,OS 永遠不會把卡送到 backupTW,只能靠使用者手動掃碼/貼上
- 政策窗口風險真實:TWDIW 目前無法分辨皮夾(client_id 是回音),一旦補 wallet attestation,用 moda_dw 的第三方皮夾會一夜失效——M5 與上游回報要趁窗口做
- 上游回報是不可逆對外動作:送錯身分、A2 若已被上游修好、A4 措辭被讀成指控,都會傷及其餘條目可信度與社群信譽,送出前的身分/條數/現況必須使用者定
- 保存 MyData 明文個資仍是產品與法遵風險；雖已放在不備份、Data Protection 保護且可單項刪除的 Application Support archive，仍需實機確認鎖定／刪除行為並定期重審保存必要性
- 非標準揭露的寬鬆化若沒把『digest 承諾驗證』和『欄位可顯示性』切乾淨,可能誤放偽造揭露,是整張卡信任的紅線
- 撤銷快照上鏈錨定與 nullifier 去重兩個離線/去重洞都指向同一個不存在的 bonds 後端,單點依賴;上游是否已排程匯出公開訊號(zk_last_signals 對等物)也未知,沒有它 smtRoot 錨定與 nullifier 去重都做不了
- docs 顯示 MyData 與若干功能歷史上多次『文案改了行為沒改』『修一半』,保險箱這種跨模型/儲存/UI 的大改容易再度只做半套;UX 稽核也警告 Wall/TWDIW/ZK 那批字串會在某次 commit 後靜默生效而沒有測試轉紅

### MyData 資料保險箱

> **歷史基線：**以下是 2026-08-27 尚未建立 archive 時的原始稽核，不是當前實作清單。已完成的八項目、受保護原始檔、清單／詳情／更新／刪除與指紋重驗，請以文首 2026-08-31 現況為準。

MyData 這條線「能跑」，但跑的不是資料保險箱，而是「領一份國民身分證資料 → 自簽成一張 national-id VC」的單一流程。MyDataWebViewController 用 WKWebView 直連 mydata.nat.gov.tw 的單一寫死端點 API.idPhotoRev，下載加密 zip（戶籍謄本 PDF）、以身分證號當解壓密碼、解析五個欄位後，把原始資料「立刻銷毀」（MyDataScratch.purge），只留下一張自簽 VC。這與「把個資帶進 app 當保險箱」正好相反——現況是隱私優先地把個資丟掉，而非保存。沒有 MyData 官方 API/OAuth 介接、沒有資料項目目錄、沒有 MyData 資料的持久化模型與瀏覽 UI。PDFSignatureScan 不是保險箱這條線，是判斷「要不要自簽」的診斷探針。
