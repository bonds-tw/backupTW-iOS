**2026-08-16 第四批：組 F 四條——「失敗完全沒有畫面」。**

- **c-1**：兩個掃描 closure 都用 `try?` 把理由丟掉。`ZKLinkEngagement` 為了能
  講出「那是另一種查驗的碼」，**特地在所有欄位檢查之前先判 `isACardSignedRequest`**
  ——然後呼叫端把那個 case 扔了。結果是拿相機對著一張有效的、我們自己的碼，

- **c-2**：最後一塊 frame 在做 inflate 與 digest **之前**就存進 `chunks`，

  **這個傳輸永遠不可能再成功，而畫面停在「接收中… 100%」，因為 collector 真的
  就是這麼認為的。** QR 那條路的 `FrameCollector` 在完全相同的位置 reset。
  加了測試釘住「失敗之後同一個 collector 要能重試成功」。
  UI 那半分兩層：parse 失敗是噪音（房間裡別人的封包），**重組失敗不是**。
- **c-3**：`BluetoothLinkPeripheral` 沒有 `didUnsubscribeFrom`，所以查驗方斷線後
  `pump()` 再也不被呼叫——持證人的畫面停在「傳送… 47%」，只要他願意一直舉著。
  而 `didSubscribeTo` 的 `guard subscriber == nil` 讓重連也接不回來：
  傳輸永久結束了，App 看起來還在忙。查驗端那半也修了——原本
  `error != nil` 才回報，而**持證人按 Done 就是一次乾淨的斷線**，
  也就是最常見的那種，完全沉默。對方掛得禮不禮貌不是查驗者需要知道的事，
  證明有沒有到才是。
- **c-17**：`PackagingError` 有四個 UI 出口卻沒有 `LocalizedError`，
  實測讀到的是「無法完成作業。（backupTW.ZKProofPackage.PackagingError錯誤1 。）」，
  另一個出口則把 `unsupportedVersion(3)` 原文印在中文句子底下。
  **而且分類還錯了方向**：一份因為「比較新」而讀不了的證明被講成對方的檔案壞掉，
  等於把唯一能修好它的人（更新 App 的那個）送去責怪一個證明完全正常的人。
  這跟 a-6 的時鐘指控是同一類錯誤。

**2026-08-16 第五批：組 G 剩下的四條——舉著手機的那個人。**

（c-7 的 idle timer 在第三批做掉了，這裡是其餘四條。）

- **c-6**：進度條原本是 `(index+1)/count`——**六秒填滿、跳回 0.08、再來一次**，
  只要那個人還站在那裡。而他正是唯一讀不到旁邊文字的人（螢幕朝著對方），
  所以那條條是他一眼唯一能吸收的東西，而它說的是「一個迴圈」。
  更糟的是它**暗示了朝某處前進**，但它量的是「在一輪裡的位置」，
  那不是朝任何地方前進。改成量「這支手機真的知道的事」——已經至少顯示過一次的張數，
  只增不減，滿了就停在那裡。
- **c-14**：1.8 Hz、滿亮度、舉在陌生人面前、跑幾輪都不能停。
  **這不是在主張它有癲癇風險**（低於 WCAG 2.3.1 的三閃門檻），
  但 2.2.2 的豁免免除的是「必須能停止」，不是「可以不給控制權」。
  現在**不論設定為何都有暫停鍵**，而且 Reduce Motion 時把間隔加倍——
  對掃描器是安全的，因為配速的理由本來就是「30fps 的相機要能對每張看上十幾眼」，
  慢一點只會更多。代價是一輪變長，所以那句「約 N 秒」改成問同一個函式，
  不是各自記一個常數。
- **c-5**：全 repo 觸覺／聲音 API 零筆，而指示句寫著「請把螢幕拿穩，
  直到查驗方的手機說全部收到為止」——此刻兩個螢幕都朝著查驗者。
  **只在 `.finished` 發一次成功觸覺**，因為那是唯一「對方真的確認收到」的狀態。
  抽成 `PresentationHaptics` 不是為了包裝 API，是為了把規則放在下一個
  想加觸覺的人會先看到的地方：下一個明顯的要求是「輪播跑完一輪也震一下」，
  而那是一個意思為「已顯示」的震動，持有人會合理地聽成「成功了」。
- **c-18**：這個檔案的檔頭自己量到 398,181 bytes ÷ 13.8 kB/s = 21.7 秒，
  螢幕上四行字沒有一行提到時間；而憑證那邊為了一個短三倍的循環特地算出「約 N 秒」。
  這還是一個**隨手往下滑就會關掉、順便把電台關掉**的 modal sheet，
  而沒有預期值的人正是會滑的那個人。

## 三、明確不建議做的

1. **不要把 reduce motion 下的輪播改成手動「下一張」**（視角2-#10 的具體做法）。開了 reduce motion 的人正把螢幕朝外舉著，看不到那顆按鈕；14 張要點 14 次，等於把一個不需要手的動作變成需要手的動作，比自動輪播更糟。可做的是：**不論設定為何都給暫停／續播鍵**，reduce motion 時把 `frameInterval` 拉長而不是停掉，並讓「轉完一輪約 N 秒」跟著重算。

2. **不要把輪播進度條換成 indeterminate**（視角1-#3 的第一方案）。轉圈在 iOS 讀作「正在處理，請等待」，同樣是一個交付不了的暗示，只是換一種。採它的第二方案。

3. **不要把揭露那一列整列變成可點**（視角2-#9 自己已經否決，但這是 review 時最自然會被提出的「改進」）。這個畫面刻意讓每一次揭露是一個動作；AX5 下 237pt 全活會製造誤觸式揭露。要放大的是命中目標，不是列。

4. **不要把 `true` 翻成「是」**（視角5-#3 的值那半）。查驗端的紀律是原樣引述對方的位元組；標題有了中文名字之後 `true` 對照得起來就夠了，翻譯值等於把 App 的話塞進對方文件的嘴裡。

5. **不要為了「這個版本拿不到查驗檔案」就把首頁那一列藏起來**。藏起來等於不說。要做的是把暫時性的「尚未」換成永久的事實。

6. **`noPendingRequest` 的中性化必須是新增分支，不能是改共用樣式**。改 `PresentationUI.verdict` 或把紅色條件化，會在下一次重構把真正的拒絕一起降級——那就是把紅色拿掉。要有測試釘住 `.rejected` 仍是 ⛔️／`.systemRed`。

7. **不要在純 QR 路徑上發任何「送出成功」的訊號**（觸覺、聲音、文案都算）。那條路上這支手機沒有任何憑據知道對方收到了。觸覺只能掛在 `BluetoothLinkState.finished`，而且該時刻的文案必須維持「對方的手機已經拿到證件了」——**收到 ≠ 通過**，這一步在實作時最容易滑掉。

8. **不要接受視角1-#2 對輪播指示句的改寫**（「請把螢幕拿穩，直到查驗方的手機說全部收到為止」→「查驗方會告訴你可以收起來」）。原句解釋了為什麼要拿穩，改寫把理由拿掉、資訊變少。要加的只有後半那句「已完整輪播 N 次」，原句留著。

9. **`footnote` 與 `caveatGroup` 的顏色要同一次改完**，否則兩層階層會被洗成同一層或反轉第二次。特別提醒：`.footnote` 目前也承載「『未通過』不等於偽造」那一句，它變深是這次改動最重要的副作用，不要在 review 時被當成「那句不重要」而排除。

10. **`ZKVerify` 收起配對 QR 時不要連 `codeCaptionLabel` 一起收**——先確認那句裡沒有可連結性警語（「這不是一次性亂數」那類）。收的必須只有已經失效的圖，不是任何一句話。

11. **任何「把但書收進展開箭頭／改小字／移到判定下方以外」的變體一律拒絕。** 這次清單裡沒有人提出，但 (b) 段每一條讀起來都像「但書太多太擠」——正確的解法一律是往上搬、加深、拆開，不是收合。

## 四、建議先做的三件

**第一件：`VerifierViewController` 結果頁與生命週期，四條判定誤讀一次改完（a-1、a-2、a-3、a-6）**
四條全部落在判準 (a)，全部在同一個檔案的同一段（`viewWillAppear` 與 `switch outcome`），合計改動量遠小於逐條分散處理。其中 a-2 是整份清單裡**唯一被兩個視角用不同方法獨立重現的缺陷**（一邊用 `CIDetector` 把 render 出來的 QR 解回去比對 challenge，一邊從 lifecycle 與 `session` 呼叫順序推導），證據強度最高；而它同時是唯一一條「App 自己的動作被說成對方的嫌疑」。順手把 a-3 缺席的那句 footnote 補回去。

**第二件：讓但書真的到得了讀者（b-3、b-4、b-1）**
b-3 與 b-4 加起來是兩行 `textColor`，影響全 App 每一條但書，而且是整份清單裡唯一**物理上讀不到**的原因——1.70:1 與 3.44:1 都不過 AA，而且只在淺色模式壞，也就是只在白天的櫃檯壞。b-1 是把已經放對位置、已經是 body 字級、已經沒被截斷的但書變成讀得懂的，同時把 `LocalizationCoverageTests` 漏掉 `PresentationScenario` 那個洞補起來，防止下次再漏。三條都不動任何但書的位置、字級或收合狀態。

**第三件：`ZKVerifyViewController` 一次重構（b-2、b-5、a-4，含視角2-#3 的判定上色）**
四個獨立視角都指到這同一個畫面，而四條的修法互相依賴：改用 `PresentationUI.verdict` 與 `PresentationUI.caveatGroup` 同時解決 1.99:1 的判定行、363 字單一 label、以及與憑證路徑的樣式落差；版面重排讓判定與但書落在第一屏（現在 AX5 下判定在畫面外 322pt，是判準 (b) 最嚴重的實例）。a-4 的三行是同一段 `stated()` 組出來的，跟拆解 detail label 是同一次改動，單獨改反而要碰兩次。

**如果要加第四件，是 d-1**：兩個畫面各加一行 `PrivacyShieldedScreen` conformance，加上把 `PrivacyShieldTests` 的寫死清單改成真的涵蓋。它是整份清單裡唯一後果**不可回復**的一條（身分證統一編號與戶籍地址進 app switcher 快照），而修法是兩行。
